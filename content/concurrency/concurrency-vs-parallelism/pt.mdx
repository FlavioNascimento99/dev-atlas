title: "Concorrência vs Paralelismo"
description: "Entenda a diferença entre execução concorrente e execução paralela."

<ArticleSection id="overview">

Imagine alguém fazendo o jantar sozinho. O arroz está no fogo, o forno está esquentando e, no meio-tempo, essa pessoa pica os legumes. Ela nunca faz duas coisas no mesmo instante, mas os três pratos andam, porque ela troca de tarefa sempre que uma delas precisa esperar.

Agora imagine três cozinheiros na mesma cozinha, cada um fazendo um prato. Aí sim três coisas acontecem no mesmo instante.

A primeira cozinha é **concorrência**, uma forma de *estruturar* um programa: o trabalho é dividido em tarefas que executam de forma independente e cujos ciclos de vida se sobrepõem. A segunda é **paralelismo**, uma forma de *executar* um programa: várias computações rodam no mesmo instante, em unidades de processamento distintas.

O resumo de Rob Pike é o mais lembrado: <Mark variant="highlight" tone="brand">concorrência é lidar com muitas coisas ao mesmo tempo, paralelismo é fazer muitas coisas ao mesmo tempo</Mark>.

Os dois resolvem problemas diferentes. Concorrência atende programas que precisam administrar muitas atividades que começam, esperam e terminam em momentos imprevisíveis, como um servidor que mantém milhares de conexões. Paralelismo atende computações que demoram demais num único núcleo e podem ser divididas para que vários núcleos as terminem antes.

<Callout type="important">
Concorrência não exige execução simultânea. Um único núcleo de CPU pode executar muitas tarefas concorrentes alternando entre elas, e um design concorrente pode ou não acabar rodando em paralelo.
</Callout>

</ArticleSection>

<ArticleSection id="how-it-works">

Existem alguns jeitos de colocar várias tarefas para andar, e todos têm um paralelo na cozinha.

**Intercalação em um núcleo.** O sistema operacional dá a cada thread o seu próprio program counter e os seus registradores: tudo o que é preciso para lembrar onde aquela tarefa parou. Para trocar de uma thread para outra no mesmo processador, ele faz uma <Mark variant="underline" tone="teal">troca de contexto</Mark> (context switch): o estado dos registradores da thread em execução é salvo e o da próxima é restaurado.

Uma interrupção de timer permite que o SO faça isso mesmo quando a thread em execução nunca cede a vez. Aqui a pessoa cozinhando sozinha deixa de ser uma comparação perfeita: ela decide quando trocar de tarefa, enquanto o SO pode tirar uma thread do núcleo a qualquer momento. De um jeito ou de outro, todas as threads avançam, embora só uma execute a cada instante.

**Intercalação cooperativa.** Event loops e runtimes de `async`/`await` obtêm a mesma sobreposição sem preempção, ou seja, sem ninguém forçar a troca. Uma tarefa executa até chegar a um ponto em que precisa esperar, devolve o controle ao loop e é retomada quando o resultado fica pronto. É quem cozinha sem ficar parado olhando a água ferver.

O Node.js funciona assim: o event loop dele delega as operações de I/O ao kernel do sistema e enfileira o callback correspondente quando o kernel avisa que a operação terminou. É dessa forma que uma única thread de JavaScript atende muitas requisições.

**Execução simultânea.** Com mais de um núcleo, o escalonador pode colocar tarefas prontas em núcleos diferentes para que executem ao mesmo tempo. São os cozinheiros extras. O runtime do Go faz isso com goroutines: `GOMAXPROCS` limita quantas threads do sistema operacional podem executar código Go simultaneamente, e o valor padrão dele é derivado do número de CPUs lógicas disponíveis para o processo.

**O limite do ganho com paralelismo.** Contratar mais cozinheiros não adianta se todo prato precisa passar pelo mesmo forno. <Mark variant="underline" tone="amber">Paralelismo só acelera a parte do programa que realmente pode ser dividida</Mark>.

A **lei de Amdahl** coloca isso em números: se uma fração `f` do trabalho é paralelizável em `n` núcleos, o speedup é `1 / ((1 - f) + f / n)` e nunca ultrapassa `1 / (1 - f)`. Um programa 90% paralelizável roda cerca de 4,7 vezes mais rápido em 8 núcleos e jamais passa de 10 vezes, não importa quantos núcleos existam.

</ArticleSection>

<ArticleSection id="when-to-use">

A pergunta a fazer é simples: o seu programa passa a maior parte do tempo *esperando* ou *calculando*?

Use **concorrência** quando o programa passa a maior parte do tempo esperando ou precisa reagir a várias fontes de eventos:

- Servidores de rede e API gateways que mantêm muitas conexões abertas.
- Interfaces de usuário que precisam continuar responsivas enquanto um download ou uma consulta está em andamento.
- Pipelines que coordenam estágios independentes, como produtores e consumidores em torno de uma fila.

Use **paralelismo** quando o gargalo é computação e o trabalho se divide em partes praticamente independentes:

- Processamento de uma coleção grande em que cada item é tratado isoladamente (lotes de imagens, arquivos de log, execuções de simulação).
- Cargas numéricas, como operações com matrizes.
- Builds e suítes de teste, em que unidades independentes compilam ou executam separadamente.

</ArticleSection>

<ArticleSection id="when-not-to-use">

Dividir o trabalho sempre tem um preço, do mesmo jeito que uma cozinha lotada precisa de coordenação. Evite nestes casos:

- **Cargas pequenas.** Criar tarefas, mover dados entre elas e combinar os resultados tem um custo. Em trabalhos curtos, esse custo é maior do que o tempo economizado.
- **Trabalho majoritariamente sequencial.** Se cada passo depende do anterior, a fração paralelizável é pequena e a lei de Amdahl limita o ganho a quase nada.
- **Paralelismo para código limitado por I/O.** Um programa esperando a rede não está com falta de CPU; <Mark variant="highlight" tone="amber">mais núcleos não fazem um serviço remoto responder mais rápido</Mark>. Nesse caso, a ferramenta certa é concorrência.
- **Concorrência para um script linear simples.** Se há uma coisa a fazer por vez, um programa sequencial é mais fácil de ler, testar e depurar.

<Callout type="warning">
Adicionar threads a um programa em que todas disputam o mesmo lock costuma deixá-lo mais lento, não mais rápido: as threads continuam executando uma por vez e ainda pagam por trocas de contexto e pela passagem do lock.
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Concorrência**

- Vantagens: mantém o programa responsivo enquanto ele espera, aproveita o tempo ocioso e muitas vezes modela o problema de forma mais natural, porque cada atividade é escrita como uma tarefa própria.
- Desvantagens: a ordem de execução deixa de ser fixa, então o resultado pode depender do timing. O estado compartilhado precisa ser protegido, e bugs como race conditions e deadlocks são difíceis de reproduzir.

**Paralelismo**

- Vantagens: reduz o tempo de relógio de trabalhos limitados por CPU e usa hardware que, de outra forma, ficaria ocioso.
- Desvantagens: o ganho é limitado pela fração sequencial do programa, a coordenação consome parte do benefício, e o tempo total de CPU e o uso de memória aumentam mesmo quando o tempo decorrido diminui.

</ArticleSection>

<Mark variant="underline" tone="brand">A escolha do mecanismo importa tanto quanto a escolha do modelo.</Mark> Threads preemptivas podem rodar em paralelo, mas exigem locks em torno dos dados compartilhados. Um event loop de thread única evita a maior parte dos locks, porém uma única computação longa bloqueia todas as outras tarefas. Processos separados isolam a memória e evitam bugs de estado compartilhado, ao preço de uma inicialização mais lenta e de serializar dados para se comunicar.

</ArticleSection>

<ArticleSection id="real-world-examples">

- **Node.js** executa JavaScript numa única thread por padrão e depende do event loop para ter concorrência, delegando o I/O ao kernel. Ele é concorrente sem executar JavaScript em paralelo.
- **Go** trata concorrência como recurso da linguagem. Os programas são escritos como goroutines, e o runtime decide quantas executam em paralelo, até o limite de `GOMAXPROCS`. O mesmo programa é concorrente em um núcleo e, em vários, concorrente e paralelo.
- **CPython** mostra que threads não implicam paralelismo. O global interpreter lock (GIL) dele permite que apenas uma thread execute código Python por vez, de modo que threads servem para tarefas limitadas por I/O, enquanto o trabalho limitado por CPU vai para `multiprocessing` ou `ProcessPoolExecutor`. Desde o Python 3.13, uma build free-threaded pode desabilitar o GIL, mas ela não é o padrão.

</ArticleSection>

<ArticleSection id="implementation-examples">

Goroutines em Go são concorrentes por definição. O programa abaixo inicia três tarefas e espera por elas; se elas rodam em paralelo depende dos núcleos disponíveis, não do código. (`WaitGroup.Go` exige Go 1.25 ou superior.)

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := range 3 {
		wg.Go(func() { fmt.Println("task", i) })
	}
	wg.Wait()
}
```

Agora, concorrência numa única thread com o `asyncio` do Python: a cozinha de uma pessoa só, em código. As três esperas de um segundo se sobrepõem, então o programa termina em cerca de um segundo, e não em três:

<CodeBlock
  language="python"
  lineNumbers
  code={`import asyncio

async def fetch(n: int) -> int:
    await asyncio.sleep(1)
    return n

async def main() -> None:
    results = await asyncio.gather(*(fetch(n) for n in range(3)))
    print(results)

asyncio.run(main())`}
/>

<Callout type="tip">
`asyncio` oferece concorrência, não paralelismo, e se encaixa em código limitado por I/O. Para trabalho de CPU em paralelo no Python, use `concurrent.futures.ProcessPoolExecutor`.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"Concorrente e paralelo são sinônimos."** Um programa concorrente pode nunca rodar em paralelo (uma máquina de um núcleo, um event loop de thread única), e uma computação paralela, como um loop vetorizado, pode não envolver nenhum design concorrente.
- **"Mais threads significa mais velocidade."** O speedup é limitado pela fração sequencial do trabalho e pela disputa por recursos compartilhados. A partir desse ponto, threads extras só acrescentam overhead.
- **"Código async roda em paralelo."** `async`/`await` intercala as tarefas nos pontos de espera. <Mark variant="highlight" tone="amber">Uma função pesada em CPU dentro de uma tarefa async bloqueia o loop inteiro.</Mark>
- **"Concorrência precisa de vários núcleos."** Sistemas operacionais já executavam muitos programas concorrentemente em máquinas de um único processador, alternando entre eles.
- **"Threads sempre rodam em paralelo."** Depende do runtime: no CPython, as threads se revezam para executar código Python sob o GIL.

</ArticleSection>
