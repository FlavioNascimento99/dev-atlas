---
title: "CI/CD"
description: "Automating the integration, testing and delivery of software changes."
---

<ArticleSection id="overview">

**CI/CD** names three related practices that shorten the path from a code change to running software:

- **Continuous Integration (CI):** every developer merges into a shared mainline at least once a day, and each merge is verified by an automated build that includes tests.
- **Continuous Delivery (CD):** the software is kept in a state where any version can be released to production at any time, with a push-button deployment.
- **Continuous Deployment:** every change that passes the automated pipeline is released to production without a human decision.

The problem they solve is late, painful integration. When work stays isolated for weeks, merging it is unpredictable and releasing it is a risky event. Integrating and releasing in small, frequent steps makes each step cheap to verify and easy to undo.

<Callout type="info">
The "CD" in CI/CD is ambiguous on purpose: it can mean delivery or deployment. Continuous deployment requires continuous delivery, but not the other way around.
</Callout>

</ArticleSection>

<ArticleSection id="how-it-works">

The core mechanism is a **deployment pipeline**: an automated sequence of stages that every change goes through, each stage giving more confidence at a higher cost in time.

- **Commit stage.** A push to the mainline triggers a build on a CI service, in a reference environment rather than on a developer's machine. It compiles, runs fast tests and static checks. Martin Fowler cites the Extreme Programming guideline of a ten-minute build for this stage.
- **Later test stages.** Slower suites, such as integration and acceptance tests, run against the artifact produced earlier, ideally in an environment that mirrors production.
- **Release stages.** The same artifact is promoted through environments until production. In continuous delivery the last promotion is a manual trigger; in continuous deployment it is automatic.

The pipeline only works on top of a few team practices described by Fowler: everything needed to build lives in version control, the build is automated and self-testing, a broken mainline is fixed immediately (reverting the offending commit is usually the first step), and unfinished work is hidden behind techniques such as feature flags instead of being kept on long-lived branches.

CI services express a pipeline with a small set of concepts. In GitHub Actions, a **workflow** is a YAML file triggered by an **event** such as a push or a pull request. It contains **jobs**, each a list of **steps** executed in order on a **runner**. Jobs run in parallel unless one declares a dependency on another.

</ArticleSection>

<ArticleSection id="visual-demonstration">

The path of a single commit through a typical pipeline:

1. A developer pulls the mainline, runs the build locally and pushes a small change.
2. The push event triggers the pipeline. A runner checks out that exact commit.
3. The commit stage installs dependencies, compiles, lints and runs unit tests. A failure stops the pipeline and notifies the team.
4. A deployable artifact (a package or a container image) is built once and stored.
5. Slower stages run integration and acceptance tests against that artifact.
6. The artifact is deployed to a production-like environment.
7. Production release: a person approves it (continuous delivery) or it happens automatically (continuous deployment), often starting with a small canary before the full rollout.

The detail that matters is step 4: later stages test and deploy the same artifact, never a rebuild.

</ArticleSection>

<ArticleSection id="when-to-use">

- **Any codebase with more than one contributor.** The more people change the same code, the more frequent integration pays off.
- **Services released often.** Smaller releases carry fewer changes, which makes testing and troubleshooting easier.
- **Projects that must work on several platforms or versions.** A job matrix runs the same checks across combinations that nobody tests by hand.
- **Environments that need traceability.** A pipeline records which change was built, tested and deployed, by whom and when.

</ArticleSection>

<ArticleSection id="when-not-to-use">

CI is rarely the wrong choice; the level of automation after it is what varies.

- **Continuous deployment without trustworthy tests.** Automatic release only moves faster whatever the test suite lets through.
- **Continuous deployment when release timing is a business decision.** Fowler notes that a team can be able to deploy frequently and still choose not to. Continuous delivery covers that case.
- **Throwaway code.** A one-off script or a prototype that will be discarded does not repay the cost of building a pipeline.
- **Running a CI server on long-lived feature branches and calling it CI.** Fowler calls this semi-integration: branches are verified in isolation, and the integration risk remains.

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Advantages**

- Integration problems surface within minutes or hours, while the change is small and fresh in its author's mind.
- Releases become routine and lower-risk, because each one carries few changes and the deployment path is exercised constantly.
- Progress is believable: work counts as done when it runs in a production-like environment.
- Real users see changes sooner, which gives earlier feedback on whether a feature is valuable.

**Disadvantages**

- It requires a substantial automated test suite, and that suite must be maintained.
- The pipeline is production infrastructure: it needs upkeep, secrets management and capacity.
- Slow or flaky stages erode the practice; people stop trusting a build that fails at random.
- Integrating unfinished work demands discipline with feature flags and incremental design.

</ArticleSection>

- **Feedback speed versus coverage.** A complete test run can be too slow for the commit stage. The usual answer is to split the pipeline: a fast commit build first, slower stages after.
- **Speed versus stability.** DORA's research treats this as a false trade-off: top performers do well on throughput and on stability metrics at the same time.
- **Feature flags versus branches.** Flags enable daily integration of unfinished work, but each flag is a code path that must be tested and eventually removed.

</ArticleSection>

<ArticleSection id="real-world-examples">

- **Google.** The release engineering chapter of the SRE book describes hermetic builds with Blaze (open-sourced as Bazel), so that results do not depend on what is installed on the build machine. Releases are cut from the mainline at a specific revision, and fixes are cherry-picked into the release branch. Some teams adopt "Push on Green", deploying every build that passes all tests, and rollouts typically begin with a canary.
- **GitHub Actions.** Pipelines are defined as workflow files in a repository's `.github/workflows` directory and executed on GitHub-hosted or self-hosted runners.
- **DORA metrics.** Teams measure delivery performance with change lead time, deployment frequency, failed deployment recovery time, change fail rate and deployment rework rate.

</ArticleSection>

<ArticleSection id="implementation-examples">

A minimal GitHub Actions workflow with a commit stage and a deployment that runs only for the mainline, after the tests pass:

```yaml
# .github/workflows/pipeline.yml
name: pipeline

on:
  push:
    branches: [main]
  pull_request:

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
      - run: npm ci
      - run: npm run lint
      - run: npm test

  deploy:
    needs: verify
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v7
      - run: ./scripts/deploy.sh
```

`needs` creates the stage order: `deploy` waits for `verify` and is skipped if it fails. Pull requests run only `verify`, giving feedback before the merge.

<Callout type="tip">
Whether this workflow is continuous delivery or continuous deployment depends on one setting: if the `production` environment is configured to require an approval, a person triggers the release; otherwise every green push ships.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"We have a CI server, so we do CI."** CI is a team practice: integrating into the mainline at least daily and keeping it green. A tool that builds isolated branches does not provide it.
- **"CD means every commit goes to production."** That is continuous deployment. Continuous delivery only requires that every commit *could* go to production.
- **"Releasing faster makes software less stable."** DORA's data shows throughput and stability improving together, largely because small changes are easier to verify and to roll back.
- **"A green pipeline means the change is safe."** A pipeline proves only what its tests check. Canary releases and the ability to roll back cover what tests miss.
- **"CI/CD is the operations team's job."** Fowler stresses that continuous delivery depends on collaboration between everyone involved in delivery, not only on automation.

</ArticleSection>
