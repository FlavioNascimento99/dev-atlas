title: "CI/CD"

<ArticleSection id="overview">

Imagine uma fábrica de carros em que cada equipe monta a sua peça em casa, durante semanas. No dia do lançamento, todo mundo aparece e tenta encaixar tudo. A porta não fecha, o motor não cabe, e ninguém sabe qual mudança quebrou o quê.

Fábricas de verdade não funcionam assim. As peças entram o tempo todo em uma linha de montagem compartilhada, e <Mark variant="highlight" tone="brand">postos de inspeção conferem cada carro antes de ele sair</Mark>. Times de software copiaram essa ideia e deram a ela o nome de **CI/CD**.

CI/CD reúne três práticas relacionadas que encurtam o caminho entre uma mudança de código e o software rodando:

- **Continuous Integration (CI):** cada desenvolvedor faz merge em uma mainline compartilhada pelo menos uma vez por dia, e cada merge é verificado por um build automatizado que inclui testes.
- **Continuous Delivery (CD):** o software é mantido em um estado no qual qualquer versão pode ser liberada para produção a qualquer momento, com um deploy acionado por um botão.
- **Continuous Deployment:** toda mudança que passa pelo pipeline automatizado é liberada para produção sem uma decisão humana.

O problema que elas resolvem é a integração tardia e dolorosa, o caos do dia do lançamento na fábrica. Quando o trabalho fica isolado por semanas, o merge vira uma loteria e o release vira um evento arriscado. <Mark variant="underline" tone="brand">Integrar e liberar em passos pequenos e frequentes</Mark> torna cada passo barato de verificar e fácil de desfazer.

<Callout type="info">
O "CD" de CI/CD é ambíguo de propósito: pode significar delivery ou deployment. Continuous deployment exige continuous delivery, mas o contrário não é verdadeiro.
</Callout>

</ArticleSection>

<ArticleSection id="how-it-works">

A linha de montagem do software se chama <Mark variant="underline" tone="teal">deployment pipeline</Mark>: uma sequência automatizada de estágios pela qual toda mudança passa. Cada estágio dá mais confiança, a um custo maior de tempo. As verificações rápidas vêm primeiro; as lentas, depois.

- **Estágio de commit.** Um push para a mainline dispara um build em um serviço de CI, em um ambiente de referência e não na máquina de um desenvolvedor. Ele compila, executa testes rápidos e verificações estáticas. Martin Fowler cita a diretriz do Extreme Programming de um build de dez minutos para este estágio.
- **Estágios de teste posteriores.** Suítes mais lentas, como testes de integração e de aceitação, rodam contra o **artefato** produzido antes: o resultado empacotado do build, pronto para rodar. Na fábrica, ele é o carro que avança pela linha. O ideal é que esses testes rodem em um ambiente que espelha a produção.
- **Estágios de release.** O mesmo artefato é promovido entre ambientes até a produção. Em continuous delivery, a última promoção é um acionamento manual; em continuous deployment, é automática.

Uma linha de montagem só funciona se as pessoas em volta dela seguem algumas regras, e com o pipeline é igual. Fowler descreve as práticas de time em que ele se apoia:

- Tudo o que é necessário para o build fica no controle de versão.
- O build é automatizado e testa a si mesmo.
- Uma mainline quebrada é corrigida imediatamente. <Mark variant="highlight" tone="amber">Reverter o commit causador costuma ser o primeiro passo.</Mark>
- O trabalho inacabado fica escondido com técnicas como feature flags, em vez de morar em branches de longa duração.

Os serviços de CI descrevem um pipeline com poucos conceitos. No GitHub Actions, um **workflow** é um arquivo YAML disparado por um **evento**, como um push ou um pull request. Ele contém **jobs**, cada um com uma lista de **steps** executados em ordem em um **runner**, a máquina que faz o trabalho. Os jobs rodam em paralelo, a menos que um declare dependência de outro.

</ArticleSection>

<ArticleSection id="when-to-use">

Se mais de uma pessoa mexe no código, ou se o código vai para produção mais de uma vez, um pipeline costuma se pagar. Ele combina especialmente com:

- **Qualquer base de código com mais de um contribuidor.** Quanto mais pessoas alteram o mesmo código, mais a integração frequente compensa.
- **Serviços liberados com frequência.** Releases menores carregam menos mudanças, o que facilita os testes e a investigação de problemas.
- **Projetos que precisam funcionar em várias plataformas ou versões.** Uma matriz de jobs roda as mesmas verificações em combinações que ninguém testa à mão.
- **Ambientes que precisam de rastreabilidade.** Um pipeline registra qual mudança foi construída, testada e implantada, por quem e quando.

</ArticleSection>

<ArticleSection id="when-not-to-use">

CI raramente é a escolha errada; o que varia é o nível de automação depois dela. E aqui a imagem da fábrica pede um aviso: um posto de inspeção só pega os defeitos que foi feito para procurar. O pipeline também, e isso limita o quanto dá para automatizar.

- **Continuous deployment sem testes confiáveis.** O release automático só entrega mais rápido aquilo que a suíte de testes deixa passar.
- **Continuous deployment quando o momento do release é uma decisão de negócio.** Fowler observa que um time pode ser capaz de fazer deploy com frequência e ainda assim escolher não fazer. Continuous delivery cobre esse caso.
- **Código descartável.** Um script de uso único ou um protótipo que vai para o lixo não compensa o custo de montar um pipeline.
- **Rodar um servidor de CI em feature branches de longa duração e chamar isso de CI.** Fowler chama isso de semi-integração: as branches são verificadas isoladamente e o risco de integração continua lá. É o problema das equipes montando peças em casa, só que com um robô conferindo cada garagem.

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Vantagens**

- Problemas de integração aparecem em minutos ou horas, enquanto a mudança é pequena e está fresca na cabeça de quem a escreveu.
- Releases viram rotina e têm menos risco, porque cada um carrega poucas mudanças e o caminho de deploy é exercitado o tempo todo.
- O progresso é crível: o trabalho conta como pronto quando roda em um ambiente semelhante ao de produção.
- Usuários reais veem as mudanças mais cedo, o que antecipa o feedback sobre o valor de uma funcionalidade.

**Desvantagens**

- Exige uma suíte de testes automatizados substancial, e essa suíte precisa ser mantida.
- O pipeline é infraestrutura de produção: precisa de manutenção, gestão de segredos e capacidade.
- Estágios lentos ou instáveis corroem a prática; as pessoas deixam de confiar em um build que falha aleatoriamente.
- Integrar trabalho inacabado exige disciplina com feature flags e design incremental.

</ArticleSection>

Além do nível de automação, algumas tensões aparecem em todo pipeline:

- **Velocidade de feedback versus cobertura.** Uma execução completa de testes pode ser lenta demais para o estágio de commit. A resposta usual é dividir o pipeline: primeiro um build de commit rápido, depois os estágios mais lentos.
- **Velocidade versus estabilidade.** A pesquisa do DORA trata isso como um falso trade-off: <Mark variant="underline" tone="brand">os times de melhor desempenho vão bem em throughput e em estabilidade ao mesmo tempo</Mark>.
- **Feature flags versus branches.** As flags permitem integrar diariamente trabalho inacabado, mas cada flag é um caminho de código que precisa ser testado e, em algum momento, removido.

</ArticleSection>

<ArticleSection id="real-world-examples">

- **Google.** O capítulo de release engineering do livro de SRE descreve builds herméticos com o Blaze (aberto como Bazel), para que os resultados não dependam do que está instalado na máquina de build. Os releases são cortados da mainline em uma revisão específica, e as correções entram na branch de release por cherry-pick. Alguns times adotam "Push on Green", fazendo deploy de todo build que passa em todos os testes, e os rollouts normalmente começam com um canary.
- **GitHub Actions.** Os pipelines são definidos como arquivos de workflow no diretório `.github/workflows` de um repositório e executados em runners hospedados pelo GitHub ou self-hosted.
- **Métricas DORA.** Os times medem o desempenho de entrega com change lead time, deployment frequency, failed deployment recovery time, change fail rate e deployment rework rate.

</ArticleSection>

<ArticleSection id="implementation-examples">

Esta é uma linha pequena, com dois postos. O workflow mínimo do GitHub Actions abaixo tem um estágio de commit e um deploy que roda apenas para a mainline, depois que os testes passam:

```yaml
# .github/workflows/pipeline.yml
name: pipeline

on:
  push:
    branches: [main]
  pull_request:

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
      - run: npm ci
      - run: npm run lint
      - run: npm test

  deploy:
    needs: verify
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v7
      - run: ./scripts/deploy.sh
```

`needs` cria a ordem dos estágios: `deploy` espera por `verify` e é ignorado se ele falhar. Pull requests rodam apenas `verify`, dando feedback antes do merge.

<Callout type="tip">
Se este workflow é continuous delivery ou continuous deployment depende de uma configuração: se o ambiente `production` estiver configurado para exigir aprovação, uma pessoa aciona o release; caso contrário, todo push verde vai para produção.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"Temos um servidor de CI, então fazemos CI."** CI é uma prática de time: integrar na mainline ao menos diariamente e mantê-la verde. Uma ferramenta que faz build de branches isoladas não entrega isso.
- **"CD significa que todo commit vai para produção."** Isso é continuous deployment. Continuous delivery exige apenas que todo commit *possa* ir para produção.
- **"Liberar mais rápido deixa o software menos estável."** Os dados do DORA mostram throughput e estabilidade melhorando juntos, em grande parte porque mudanças pequenas são mais fáceis de verificar e de reverter.
- **"Um pipeline verde significa que a mudança é segura."** <Mark variant="highlight" tone="amber">Um pipeline prova apenas o que os seus testes verificam.</Mark> Releases canary e a capacidade de rollback cobrem o que os testes deixam passar.
- **"CI/CD é trabalho do time de operações."** Fowler enfatiza que continuous delivery depende da colaboração entre todos os envolvidos na entrega, não apenas de automação.

</ArticleSection>
