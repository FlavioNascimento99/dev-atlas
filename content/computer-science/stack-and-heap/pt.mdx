<ArticleSection id="overview">

Pense na sua mesa de trabalho. Na sua frente tem uma pilha de post-its: cada tarefa nova vai para o topo e, quando você termina, joga o post-it fora. No fim do corredor tem um depósito com prateleiras. Quando alguma coisa é grande demais para a mesa, ou precisa continuar existindo depois que a tarefa acabou, você aluga uma prateleira, e o atendente te entrega um ticket com o número dela.

Um programa em execução organiza a memória de um jeito bem parecido. A **stack** (pilha) e o **heap** são as duas regiões do espaço de endereçamento de um processo onde ele guarda seus dados. A stack é a pilha de post-its: ela acompanha a cadeia de chamadas de função e guarda as variáveis locais, os parâmetros e os valores de retorno.

O heap é o depósito. Ele guarda <Mark variant="underline" tone="brand">memória alocada dinamicamente</Mark>: dados cujo tamanho ou tempo de vida não dá para amarrar a uma única chamada de função.

Por que duas regiões? Porque os programas têm duas necessidades diferentes. A maioria dos valores é pequena, vive pouco e só importa enquanto uma função executa; a stack cuida deles quase sem controle adicional. Outros valores precisam sobreviver à função que os criou, crescer em tempo de execução ou ser compartilhados pelo programa. Esses exigem um alocador capaz de entregar e receber memória de volta em qualquer ordem, e é isso que o heap oferece.

</ArticleSection>

<ArticleSection id="how-it-works">

**Layout.** No modelo simplificado usado pelos livros de sistemas operacionais, um espaço de endereçamento contém o código do programa, depois o heap, e a stack na extremidade oposta. Heap e stack ficam distantes porque os dois precisam de espaço para crescer, e crescem um em direção ao outro. Essa disposição é uma convenção, não uma exigência.

**A stack** é uma estrutura last-in, first-out (o último a entrar é o primeiro a sair), igual ao último post-it da pilha. Chamar uma função empilha os parâmetros e as variáveis locais dela; esse conjunto se chama **frame**. Retornar o desempilha.

Como os dados novos sempre vão para o topo, alocar é trivial: não há busca por espaço livre, e a desalocação acontece sozinha ao fim da chamada. Em C, é por isso que a memória de stack também é chamada de memória *automática*. A restrição usual é que <Mark variant="highlight" tone="brand">um valor na stack tem tamanho conhecido e fixo em tempo de compilação</Mark>.

**O heap** é gerenciado por um **alocador**, o atendente do depósito. Quando o programa pede um bloco, o alocador encontra uma região livre grande o suficiente, marca essa região como em uso, registra informações de controle para os próximos pedidos e devolve um **ponteiro** para ela: o ticket com o número da prateleira.

O ponteiro em si tem tamanho fixo, então <Mark variant="underline" tone="teal">ele pode ficar na stack enquanto o dado para o qual aponta fica no heap</Mark>. Uma única instrução em C, como `int *x = malloc(sizeof(int));`, usa as duas regiões: o compilador reserva espaço na stack para o ponteiro `x`, e `malloc` reserva espaço no heap para o inteiro.

**Liberar memória do heap** é onde as linguagens diferem. Alguém precisa devolver a prateleira:

- Em C, o programador chama `free()` explicitamente.
- Em Rust, cada valor no heap tem um dono (owner), e a memória é devolvida automaticamente quando o dono sai de escopo.
- Em linguagens com garbage collector, como Java e Go, o runtime encontra a memória que não está mais em uso e a recupera.

**Threads.** Um processo multithread tem uma stack por thread, enquanto o heap é compartilhado: cada pessoa tem a própria pilha de post-its na mesa, mas todo mundo usa o mesmo depósito. A especificação da Java Virtual Machine diz isso com todas as letras: cada thread tem uma stack privada que armazena frames, e um único heap é compartilhado entre todas as threads.

</ArticleSection>

<ArticleSection id="when-to-use">

Onde guardar os seus dados? Quase sempre a resposta depende de <Mark variant="underline" tone="brand">tamanho e tempo de vida</Mark>.

Mantenha os dados na **stack** quando:

- O tamanho é conhecido em tempo de compilação e é pequeno.
- Eles só são necessários enquanto a função que os declara está executando.

Aloque no **heap** quando:

- O tamanho só é conhecido em tempo de execução ou muda com o tempo, como em strings e coleções que crescem.
- O dado precisa sobreviver à função que o cria.
- O dado é grande o bastante para que copiá-lo entre frames ou fazê-lo caber numa stack limitada seja uma preocupação.
- Várias partes do programa, ou várias threads, precisam acessar o mesmo objeto.

</ArticleSection>

<ArticleSection id="when-not-to-use">

Cada região tem um jeito próprio de dar problema quando usada para a coisa errada:

- **Não retorne o endereço de uma variável local.** O frame é descartado no retorno, então o ponteiro passa a se referir a uma memória que será reutilizada pela próxima chamada. É um ticket anotado num post-it que acabou de ir para o lixo.
- **Não coloque dados muito grandes ou sem limite na stack.** Stacks têm tamanho limitado. Recursão profunda ou sem limite e arrays locais grandes as esgotam; a JVM, por exemplo, lança `StackOverflowError` quando uma thread precisa de uma stack maior do que a permitida.
- **Não aloque no heap valores pequenos e de vida curta em hot paths sem motivo.** Toda alocação custa trabalho do alocador e, em runtimes gerenciados, acrescenta trabalho para o garbage collector.

<Callout type="warning">
O gerenciamento manual do heap é uma fonte clássica de defeitos em C: esquecer de liberar a memória (memory leak), usar a memória depois de liberá-la (dangling pointer) e liberar o mesmo bloco duas vezes (double free, cujo resultado é indefinido).
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Stack**

- Vantagens: alocar e desalocar é quase gratuito, a limpeza é automática e os dados ficam próximos na memória, o que os processadores tratam com eficiência.
- Desvantagens: os tamanhos precisam ser fixos em tempo de compilação, o tempo de vida fica preso à chamada e o espaço total é limitado.

**Heap**

- Vantagens: aceita dados de qualquer tamanho, com tempo de vida independente da cadeia de chamadas, e permite que diferentes partes do programa compartilhem o mesmo objeto.
- Desvantagens: a alocação é mais lenta porque o alocador precisa encontrar espaço e manter registros, o acesso passa por um ponteiro, e alguém (o programador, o compilador ou um garbage collector) precisa decidir quando a memória é liberada.

</ArticleSection>

O trade-off de fundo é <Mark variant="underline" tone="teal">flexibilidade contra custo</Mark>. A stack é rápida justamente por ser rígida: a ordem estrita last-in, first-out não deixa nada para gerenciar. O heap remove essas restrições e paga por isso em tempo de alocação, indireção e na necessidade de uma política de liberação.

Como o heap é compartilhado entre threads, é nos dados guardados nele que os problemas de sincronização aparecem, ao passo que a stack de cada thread é privada.

<ArticleSection id="real-world-examples">

- **Java Virtual Machine.** A especificação define uma stack privada por thread, formada por frames, um criado a cada invocação de método e destruído quando ela termina, e um heap do qual são alocadas todas as instâncias de classes e arrays. Objetos no heap nunca são desalocados explicitamente; um garbage collector os recupera. Se o heap não consegue atender a um pedido, a JVM lança `OutOfMemoryError`.
- **Go.** O programador não escolhe onde uma variável vive. O compilador mantém uma variável local no stack frame da função quando consegue provar que ela não é referenciada depois do retorno (escape analysis) e, caso contrário, a coloca no heap gerenciado pelo garbage collector. As stacks das goroutines começam com poucos kilobytes e são aumentadas e reduzidas pelo runtime, e é isso que torna viável ter centenas de milhares de goroutines.
- **Rust.** Uma `String` mantém um ponteiro, um comprimento e uma capacidade na stack e o texto no heap. Quando a variável dona sai de escopo, Rust chama `drop` e a memória do heap é devolvida sem garbage collector.

</ArticleSection>

<ArticleSection id="implementation-examples">

Veja a alocação em stack e em heap em C, com o bloco do heap sobrevivendo à função que o criou:

```c
#include <stdio.h>
#include <stdlib.h>

int *make_counter(void) {
    int local = 0;                      // stack: some quando a função retorna
    int *counter = malloc(sizeof(int)); // heap: sobrevive ao retorno
    if (counter == NULL) return NULL;
    *counter = local;
    return counter;                     // retornar &local deixaria um dangling pointer
}

int main(void) {
    int *c = make_counter();
    if (c == NULL) return 1;
    (*c)++;
    printf("%d\n", *c);
    free(c);                            // exatamente um free por malloc
    return 0;
}
```

A mesma ideia em Rust, em que o compilador insere a liberação por você:

```rust
fn main() {
    let n = 42;                    // stack: inteiro de tamanho fixo
    let s = String::from("hello"); // stack: ponteiro, comprimento, capacidade; heap: o texto
    println!("{n} {s}");
} // s sai de escopo aqui e sua memória no heap é liberada
```

<Callout type="tip">
Em Go, retornar um ponteiro para uma variável local é seguro: o compilador detecta que a variável escapa da função e a aloca no heap em vez da stack.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"O heap é a estrutura de dados heap."** A região de memória e a fila de prioridade baseada em árvore só compartilham o nome.
- **"Tipos de valor vão para a stack e objetos vão para o heap."** Isso é uma decisão de implementação, não uma regra da linguagem. Em Go, o local de armazenamento é irrelevante para a semântica da linguagem e é escolhido pelo compilador.
- **"Memória do heap é uma memória mais lenta."** É aqui que a imagem da mesa e do depósito engana. <Mark variant="highlight" tone="brand">As duas regiões são memória comum no mesmo espaço de endereçamento</Mark>; o heap não fica "mais longe". O custo extra dele vem de alocar, de seguir ponteiros e de os dados ficarem espalhados.
- **"Um garbage collector torna memory leaks impossíveis."** O coletor só libera o que não é mais referenciado. Se o programa mantém uma referência a um dado de que não precisa mais, essa memória nunca é recuperada.
- **"Memória que nunca é liberada está perdida para sempre."** Quando um processo termina, o sistema operacional recupera toda a memória dele, inclusive o heap. Leaks prejudicam programas de longa duração, como servidores, que aos poucos ficam sem memória.

</ArticleSection>
