---
title: "Stack and Heap"
description: "How programs organize memory for function calls and dynamically allocated data."
---

<ArticleSection id="overview">

Picture your desk at work. In front of you is a pile of sticky notes: each new task goes on top, and when you finish it, you throw its note away. Down the hall there is a storage room with shelves. When something is too big for the desk, or has to stay around after the task is done, you rent a shelf, and the clerk hands you a ticket with the shelf number.

A running program organizes its memory in much the same way. The **stack** and the **heap** are the two regions of a process's address space where it keeps its data. The stack is the pile of notes: it tracks the chain of function calls and holds their local variables, parameters and return values.

The heap is the storage room. It holds <Mark variant="underline" tone="brand">dynamically allocated memory</Mark>: data whose size or lifetime cannot be tied to a single function call.

Why two regions? Because programs have two different needs. Most values are small, short-lived and only matter while one function runs; the stack handles those with almost no bookkeeping. Other values must outlive the function that created them, grow at runtime or be shared across the program. Those need an allocator that can hand out and take back memory in any order, which is what the heap provides.

</ArticleSection>

<ArticleSection id="how-it-works">

**Layout.** In the simplified model used by operating systems textbooks, an address space contains the program code, then the heap, and the stack at the opposite end. Heap and stack are placed far apart because both need room to grow, and they grow toward each other. This placement is a convention, not a requirement.

**The stack** is a last-in, first-out structure: the last note on the pile is the first one to go. Calling a function pushes its parameters and local variables; this group is called a **frame**. Returning pops it.

Since new data always goes on top, allocating is trivial: there is no search for free space, and deallocation happens automatically at the end of the call. In C this is why stack memory is also called *automatic* memory. The usual constraint is that <Mark variant="highlight" tone="brand">a value on the stack has a size that is known and fixed at compile time</Mark>.

**The heap** is managed by an **allocator**, the clerk of the storage room. When a program requests a block, the allocator finds a free region that is large enough, marks it as in use, records bookkeeping for future requests and returns a **pointer** to it: the ticket with the shelf number.

The pointer itself has a fixed size, so <Mark variant="underline" tone="teal">it can live on the stack while the data it points to lives on the heap</Mark>. A single C statement such as `int *x = malloc(sizeof(int));` uses both: the compiler reserves stack space for the pointer `x`, and `malloc` reserves heap space for the integer.

**Releasing heap memory** is where languages differ. Someone has to give the shelf back:

- In C, the programmer calls `free()` explicitly.
- In Rust, each heap value has an owner, and the memory is returned automatically when the owner goes out of scope.
- In languages with a garbage collector, such as Java and Go, the runtime finds memory that is no longer in use and reclaims it.

**Threads.** A multi-threaded process has one stack per thread, while the heap is shared: every worker has a pile on their own desk, but they all use the same storage room. The Java Virtual Machine specification states this directly: each thread has a private stack that stores frames, and a single heap is shared among all threads.

</ArticleSection>

<ArticleSection id="when-to-use">

Which one should hold your data? It mostly comes down to <Mark variant="underline" tone="brand">size and lifetime</Mark>.

Keep data on the **stack** when:

- Its size is known at compile time and is small.
- It is only needed while the function that declares it is running.

Allocate on the **heap** when:

- The size is only known at runtime or changes over time, as with growable strings and collections.
- The data must outlive the function that creates it.
- The data is large enough that copying it between frames or fitting it in a limited stack is a concern.
- Several parts of the program, or several threads, need access to the same object.

</ArticleSection>

<ArticleSection id="when-not-to-use">

Each region has a way of biting you when used for the wrong job:

- **Do not return the address of a local variable.** The frame is discarded on return, so the pointer refers to memory that will be reused by the next call. It is a ticket written on a note that was just thrown away.
- **Do not put very large or unbounded data on the stack.** Stacks are limited in size. Deep or unbounded recursion and large local arrays exhaust them; the JVM, for instance, throws `StackOverflowError` when a thread needs a larger stack than is permitted.
- **Do not heap-allocate small, short-lived values in hot paths without reason.** Every allocation costs allocator work, and in managed runtimes it adds work for the garbage collector.

<Callout type="warning">
Manual heap management is a classic source of defects in C: forgetting to free memory (a memory leak), using memory after freeing it (a dangling pointer) and freeing the same block twice (a double free, whose result is undefined).
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Stack**

- Advantages: allocation and deallocation are nearly free, cleanup is automatic, and data stays close together in memory, which processors handle efficiently.
- Disadvantages: sizes must be fixed at compile time, lifetimes are bound to the call, and total space is limited.

**Heap**

- Advantages: supports data of any size, with a lifetime independent of the call chain, and lets different parts of a program share the same object.
- Disadvantages: allocation is slower because the allocator has to find space and keep records, access goes through a pointer, and someone (the programmer, the compiler or a garbage collector) must decide when memory is released.

</ArticleSection>

The underlying trade-off is <Mark variant="underline" tone="teal">flexibility against cost</Mark>. The stack is fast precisely because it is rigid: strict last-in, first-out order leaves nothing to manage. The heap removes those restrictions and pays for it in allocation time, indirection and the need for a release policy.

Because the heap is shared between threads, data stored there is also where synchronization problems appear, whereas each thread's stack is private to it.

</ArticleSection>

<ArticleSection id="real-world-examples">

- **Java Virtual Machine.** The specification defines a private stack per thread made of frames, one created per method invocation and destroyed when it completes, and a heap from which all class instances and arrays are allocated. Heap objects are never deallocated explicitly; a garbage collector reclaims them. If the heap cannot satisfy a request, the JVM throws `OutOfMemoryError`.
- **Go.** The programmer does not choose where a variable lives. The compiler keeps a local variable in the function's stack frame when it can prove the variable is not referenced after the function returns (escape analysis), and otherwise places it on the garbage-collected heap. Goroutine stacks start at a few kilobytes and are grown and shrunk by the runtime, which is what makes hundreds of thousands of goroutines practical.
- **Rust.** A `String` keeps a pointer, a length and a capacity on the stack and its text on the heap. When the variable that owns it goes out of scope, Rust calls `drop` and the heap memory is returned without a garbage collector.

</ArticleSection>

<ArticleSection id="implementation-examples">

Here is stack and heap allocation in C, with the heap block outliving the function that created it:

```c
#include <stdio.h>
#include <stdlib.h>

int *make_counter(void) {
    int local = 0;                      // stack: gone when the function returns
    int *counter = malloc(sizeof(int)); // heap: survives the return
    if (counter == NULL) return NULL;
    *counter = local;
    return counter;                     // returning &local would dangle
}

int main(void) {
    int *c = make_counter();
    if (c == NULL) return 1;
    (*c)++;
    printf("%d\n", *c);
    free(c);                            // exactly one free per malloc
    return 0;
}
```

The same idea in Rust, where the compiler inserts the release for you:

```rust
fn main() {
    let n = 42;                    // stack: fixed-size integer
    let s = String::from("hello"); // stack: pointer, length, capacity; heap: the text
    println!("{n} {s}");
} // s goes out of scope here and its heap memory is freed
```

<Callout type="tip">
In Go, returning a pointer to a local variable is safe: the compiler detects that the variable escapes the function and allocates it on the heap instead of the stack.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"The heap is the heap data structure."** The memory region and the tree-based priority queue only share a name.
- **"Value types go on the stack and objects go on the heap."** That is an implementation decision, not a language rule. In Go the storage location is irrelevant to the semantics of the language and is chosen by the compiler.
- **"Heap memory is slower memory."** This is where the desk-and-storage-room picture misleads. <Mark variant="highlight" tone="brand">Both regions are ordinary memory in the same address space</Mark>; the heap is not farther away. Its extra cost comes from allocating, from following pointers and from data being spread out.
- **"A garbage collector makes memory leaks impossible."** A collector only frees what is no longer referenced. If the program keeps a reference to data it no longer needs, that memory is never reclaimed.
- **"Memory that is never freed is lost for good."** When a process exits, the operating system reclaims all of its memory, including the heap. Leaks hurt long-running programs such as servers, which gradually run out of memory.

</ArticleSection>
