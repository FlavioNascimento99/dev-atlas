<ArticleSection id="overview">

**Garbage collection** (GC) is automatic memory management: the language runtime, not the programmer, decides when heap memory can be released. The program allocates objects freely, and a component called the collector identifies the ones that can no longer be used and recycles their memory.

It solves the problems of manual deallocation. Releasing memory by hand requires knowing, at every point of the program, whether anyone still needs an object. Getting that wrong in one direction leaks memory; getting it wrong in the other leaves pointers to memory that has already been reused. A collector removes that decision from application code.

Since a runtime cannot know whether a program *will* use an object again, collectors rely on a safe approximation: an object is kept while it is **reachable**, that is, while some chain of pointers leads to it from a **root** such as a local or global variable. Everything else is garbage.

</ArticleSection>

<ArticleSection id="how-it-works">

There are two fundamental families of collectors, and most production runtimes combine several techniques.

**Tracing collection** finds live objects by following pointers transitively from the roots.

- *Mark-sweep* works in two steps. The collector first walks the object graph and **marks** every object it reaches. It then **sweeps** the heap, making all unmarked memory available for new allocations. Objects stay where they are, which keeps the algorithm simple but can leave the free space fragmented.
- *Copying* and *compacting* collectors move the survivors. A semi-space collector keeps half of its space empty, evacuates the live objects into it and then swaps the roles of the two halves; a mark-compact collector relocates survivors to close the gaps left by dead objects. Both leave free memory contiguous, at the cost of copying objects and updating the pointers to them.

**Reference counting** stores in each object the number of references to it and frees the object when the count drops to zero. Memory is returned immediately, with no separate collection phase, but counting alone never frees objects that reference each other in a cycle. CPython therefore pairs reference counting with a cyclic garbage collector that detects and breaks reference cycles.

**Generational collection** is an optimization built on an empirical observation, the *weak generational hypothesis*: most objects survive for only a short period of time. The heap is split by age. New objects are allocated in a young generation that is collected often and cheaply, because most of its contents are already dead (a *minor* collection). Objects that survive several collections are promoted to an old generation, which is collected rarely in a *major* collection that involves far more objects and usually takes much longer.

**Scheduling the work.** The simplest collectors stop the application for the entire collection, a stop-the-world pause. To shorten pauses, modern collectors use three techniques: *parallel* collection, in which several threads share the work during a pause; *incremental* collection, in which the work is split into small slices interleaved with the program; and *concurrent* collection, in which collector threads run in the background while the application keeps executing.

</ArticleSection>

<ArticleSection id="when-to-use">

- **General application development.** Business services, web backends, tools and scripts benefit from not having to track ownership of every object.
- **Programs with complex object graphs.** Structures with shared ownership or cycles, such as graphs, caches and observer relationships, are hard to free correctly by hand.
- **Workloads that create many short-lived objects.** Request handling typically allocates objects that die as soon as the response is sent, which is exactly the pattern generational collectors are built for.
- **Teams prioritizing safety and delivery speed.** A whole class of memory errors disappears without code review effort.

</ArticleSection>

<ArticleSection id="when-not-to-use">

- **Hard real-time systems.** If a deadline can never be missed, any pause or scheduling delay introduced by a collector must be bounded and proven, which most general-purpose collectors do not offer.
- **Severely memory-constrained environments.** Tracing collectors need headroom above the live data to run efficiently. In Go, for example, setting `GOGC=100` makes the target heap roughly twice the size of the live heap.
- **Code that needs full control of layout and lifetime.** Kernels, allocators and some high-performance engines manage memory explicitly or through ownership rules checked by the compiler.

<Callout type="warning">
A garbage collector manages memory only. Files, sockets, locks and database connections still have to be closed explicitly; waiting for the collector to notice an unreachable object is not a release strategy for them.
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Advantages**

- Eliminates the errors of manual deallocation, such as freeing too early or freeing twice.
- Simplifies APIs: a function can return or share an object without defining who is responsible for freeing it.
- Moving collectors compact the heap, which fights fragmentation.

**Disadvantages**

- Consumes CPU time for work the program did not ask for, and that cost grows with the amount of live data that has to be traced.
- Needs extra memory, because garbage accumulates between collections.
- Can add latency through pauses or by competing with the application for CPU.
- Makes the moment of reclamation less predictable, and still allows leaks when the program keeps references to objects it no longer needs.

</ArticleSection>

<ArticleSection id="trade-offs">

Collector design is usually discussed along three measures: **throughput**, the share of total time not spent in garbage collection; **latency**, the responsiveness of the application, which pauses degrade; and **footprint**, the memory the process needs. Improving one tends to cost another. In Go, doubling `GOGC` doubles the heap memory overhead and roughly halves the CPU cost of collection. A concurrent design reduces pauses but often delivers lower throughput than an equivalent stop-the-world collector.

<ArticleSection id="real-world-examples">

- **Go** uses a non-moving, mark-sweep tracing collector that does most of its work concurrently with the application, so that global pauses are not proportional to the size of the heap. It is tuned through `GOGC`, which trades memory for GC CPU time, and through a soft memory limit (`GOMEMLIMIT`) added in Go 1.19.
- **The HotSpot JVM** ships several collectors. Serial uses a single thread, Parallel is the throughput collector, G1 is a mostly concurrent collector selected by default on most hardware and operating system configurations, and ZGC is a low-latency collector that provides maximum pause times under a millisecond at the cost of some throughput.
- **V8**, the JavaScript engine, has a generational collector named Orinoco. A scavenger collects the young generation using semi-space copying, and a mark-compact collector handles the whole heap by marking, sweeping and compacting fragmented pages. Orinoco combines parallel, incremental and concurrent techniques and can also schedule work in idle time on the main thread.
- **CPython** performs garbage collection through reference counting plus a cyclic collector, exposed to programs by the `gc` module.

</ArticleSection>

<ArticleSection id="implementation-examples">

Reference counting and the cyclic collector in CPython. Two objects that reference each other become unreachable, but their counts never reach zero, so only the cyclic collector can free them:

```python
import gc


class Node:
    def __init__(self) -> None:
        self.other: "Node | None" = None


gc.disable()             # pause automatic cycle collection for the demo
a, b = Node(), Node()
a.other, b.other = b, a  # reference cycle: a -> b -> a
del a, b                 # unreachable, yet each count is still 1
print(gc.collect())      # cyclic collector frees both: prints 2 on CPython 3.12
gc.enable()
```

Tuning is normally done through runtime settings, not code. The Go runtime reads environment variables, and the JVM selects a collector from command-line flags:

```bash
# Go: collect more often, using less memory and more CPU
GOGC=50 ./server

# Go: set a soft limit on the memory used by the runtime
GOMEMLIMIT=4GiB ./server

# Java: choose the low-latency collector
java -XX:+UseZGC -jar app.jar
```

<Callout type="tip">
The cheapest garbage is the garbage never created. Before tuning a collector, profile allocations: reducing the allocation rate lowers GC cost under any collector.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"With a garbage collector, memory leaks cannot happen."** A collector frees unreachable objects only. A cache that grows forever or a listener that is never unregistered keeps its objects reachable, and they are never reclaimed.
- **"Garbage collection means long stop-the-world pauses."** That describes the simplest collectors. Concurrent collectors do most of their work while the program runs, and collectors such as ZGC keep maximum pauses under a millisecond.
- **"Reference counting is not garbage collection."** It is one of the two classic families of automatic memory management. CPython's own documentation describes its garbage collection as reference counting plus a cyclic collector.
- **"In a garbage-collected language, everything lives on the heap."** Compilers avoid the heap when they can. In Go, values whose lifetime the compiler can determine are stack-allocated and are not managed by the collector at all.
- **"The cost of a collection depends on how much garbage there is."** The dominant cost of a tracing cycle is marking the *live* objects. A program with a large live heap pays more per cycle even if it produces little garbage.

</ArticleSection>
