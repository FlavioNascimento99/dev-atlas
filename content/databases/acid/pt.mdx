<ArticleSection id="overview">

Você faz um Pix de 100 reais para um amigo. Por trás da tela, isso são duas alterações: 100 saem da sua conta e 100 entram na dele. Agora imagine que o servidor do banco cai bem no meio das duas. Para onde foi o dinheiro?

Pense num caixa de banco à moda antiga cuidando dessa transferência. Ele anota no livro de registro o que vai fazer, prepara a papelada atrás do balcão, onde ninguém mais vê, e só carimba quando os dois lados estão prontos. Se algo der errado antes do carimbo, a papelada vai para o lixo e é como se nada tivesse acontecido.

Os bancos de dados fazem a mesma promessa a uma **transação**: um grupo de leituras e escritas tratado como uma unidade. **ACID** é o acrônimo das quatro garantias envolvidas: **Atomicidade**, **Consistência**, **Isolamento** e **Durabilidade**. O termo foi cunhado em 1983 por Theo Härder e Andreas Reuter para dar nomes precisos aos mecanismos de tolerância a falhas dos bancos de dados.

O problema que ele trata é que <Mark variant="highlight" tone="brand">as coisas dão errado no meio de alterações com várias etapas</Mark>. Se o servidor cair entre o débito e o crédito, ou se outra transação ler os saldos no meio do caminho, os dados deixam de descrever a realidade.

Sem transações, cada aplicação precisaria de código próprio para detectar e reparar cada um desses estados parciais. Com elas, a aplicação declara onde a unidade começa e termina, e o banco de dados cuida das falhas e da concorrência.

</ArticleSection>

<ArticleSection id="how-it-works">

Cada letra corresponde a um hábito do caixa.

**Atomicidade** significa tudo ou nada. Uma transação ou faz **commit**, e todas as suas escritas passam a valer, ou é **abortada**, e nenhuma delas vale. Se algo falha no meio, as etapas já executadas são desfeitas: a papelada pela metade vai para o lixo. A palavra não diz nada sobre concorrência; <Mark variant="underline" tone="teal">*abortabilidade*</Mark> a descreveria melhor.

**Consistência** significa que a transação leva o banco de dados de um estado válido a outro, em que "válido" é definido por invariantes como "débitos e créditos se equilibram". Uma **invariante** é uma regra que precisa ser verdadeira o tempo todo.

O banco de dados impõe as invariantes que lhe são informadas, como as constraints `NOT NULL`, de unicidade, de chave estrangeira e `CHECK`. O restante é responsabilidade da aplicação. <Mark variant="highlight" tone="amber">Uma transação atômica, isolada e durável ainda pode gravar dados errados.</Mark> O caixa segue as regras escritas do banco, não as que ninguém anotou.

**Isolamento** significa que transações concorrentes não enxergam o trabalho incompleto umas das outras, assim como os outros clientes não leem a papelada atrás do balcão. A forma mais estrita é a **serializabilidade**: o resultado é o mesmo que se as transações tivessem sido executadas uma após a outra.

Como isso é caro, os bancos de dados oferecem **níveis de isolamento** mais fracos. Muitos, incluindo o PostgreSQL, implementam o isolamento com <Mark variant="underline" tone="brand">controle de concorrência multiversão (MVCC)</Mark>, em que cada transação lê de um snapshot consistente em vez de bloquear quem escreve.

**Durabilidade** significa que, uma vez confirmado o commit, os dados sobrevivem a uma queda. A técnica padrão é o **write-ahead log** (WAL), o livro de registro do caixa: um registro descrevendo cada alteração é gravado em armazenamento permanente *antes* de os arquivos de dados serem modificados.

Depois de uma queda, o banco de dados reexecuta o log para refazer as alterações que não tinham chegado aos arquivos de dados. Só o log precisa ser descarregado em disco no momento do commit, e ele é escrito de forma sequencial, o que sai muito mais barato do que descarregar cada página de dados modificada.

<Callout type="info">
Aqui a analogia do caixa deixa de valer. Um caixa atende um cliente por vez, enquanto um banco de dados roda muitas transações ao mesmo tempo e muitas vezes deixa que uma enxergue mais da outra do que um caixa de verdade deixaria. Quanto elas enxergam é o nível de isolamento, assunto da seção de trade-offs.
</Callout>

</ArticleSection>

<ArticleSection id="when-to-use">

Use uma transação sempre que uma alteração feita pela metade deixaria os dados contando uma mentira:

- **Alterações que abrangem várias linhas ou tabelas e precisam concordar**: transferências de dinheiro, pedidos com reserva de estoque, agendamentos.
- **Invariantes que usuários concorrentes poderiam quebrar**: um assento vendido uma única vez, um nome de usuário usado uma única vez, um saldo que nunca fica negativo.
- **Lógica de verificar e depois agir**, em que a decisão depende de dados que outra sessão poderia alterar no intervalo.
- **Sistemas de registro**, em que o banco de dados é a autoridade e uma escrita confirmada não pode desaparecer.

</ArticleSection>

<ArticleSection id="when-not-to-use">

Transações saem baratas quando são curtas e locais. Elas ficam caras, ou deixam de ajudar, em alguns casos:

- **Trabalho demorado dentro de uma única transação.** Uma transação que fica aberta enquanto chama uma API externa ou espera um usuário retém locks ou versões antigas de linhas e atrapalha todo o resto.
- **Cargas em massa de dados que podem ser regenerados**, como um cache ou uma tabela derivada, em que relaxar a durabilidade rende muita velocidade.
- **Operações que abrangem vários serviços independentes.** Uma transação local não as cobre; coordenar uma transação entre sistemas é um problema diferente e muito mais caro.
- **O nível de isolamento mais estrito por padrão.** Serializable em tudo custa vazão e obriga a ter uma lógica de retry de que muitas cargas de trabalho não precisam.

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Vantagens**

- O tratamento de erros se reduz a um caso: diante de qualquer falha, abortar e tentar de novo.
- Uma classe inteira de bugs de concorrência é tratada pelo banco de dados, e não por cada aplicação.
- Dados confirmados sobrevivem a quedas e à falta de energia.
- O raciocínio é local: uma transação pode ser escrita como se estivesse sozinha.

**Desvantagens**

- Cada commit espera uma descarga em armazenamento estável, o que limita a vazão de escrita.
- O isolamento custa concorrência: locks causam espera e deadlocks, e snapshots causam transações abortadas que precisam ser repetidas.
- As garantias terminam na fronteira do banco de dados. E-mails enviados ou APIs chamadas dentro de uma transação não são desfeitos por um rollback.
- Estender as garantias a várias máquinas exige protocolos de coordenação com latência e modos de falha próprios.

</ArticleSection>

<ArticleSection id="trade-offs">

O principal ajuste é o nível de isolamento: quanto do trabalho alheio as transações concorrentes podem perceber. O padrão SQL define quatro níveis pelas anomalias que cada um deve impedir, e as implementações podem ser mais estritas do que o exigido. O PostgreSQL se comporta assim:

Níveis mais baixos permitem mais concorrência e expõem mais anomalias. Níveis mais altos são mais seguros e, em repeatable read e serializable, a aplicação precisa estar pronta para repetir transações que o banco de dados aborta com uma falha de serialização.

O segundo ajuste é a durabilidade. <Mark variant="underline" tone="amber">Esperar o log chegar ao disco a cada commit é o que torna o commit seguro e também o que o torna lento.</Mark> Agrupar vários commits em uma única descarga recupera vazão; confirmar antes da descarga recupera mais ainda e aceita perder as transações mais recentes em uma queda.

<Callout type="warning">
O mesmo nome de nível não significa o mesmo comportamento em todos os bancos de dados. Um artigo de 1995, "A Critique of ANSI SQL Isolation Levels", mostrou que as definições do padrão são ambíguas e não descrevem o snapshot isolation, usado por vários produtos. Leia a documentação do seu banco de dados em vez de confiar no nome.
</Callout>

</ArticleSection>

<ArticleSection id="real-world-examples">

- O **PostgreSQL** executa todo comando dentro de uma transação: sem um `BEGIN` explícito, cada comando recebe uma transação implícita, que faz commit se ele tiver sucesso. Seu nível de isolamento padrão é read committed, e seu nível serializable é implementado com Serializable Snapshot Isolation.
- O **SQLite**, uma biblioteca embutida sem processo servidor, implementa transações serializáveis que permanecem atômicas e duráveis mesmo quando interrompidas por uma falha do programa, uma falha do sistema operacional ou uma queda de energia.
- O **WAL do PostgreSQL** permite que um único `fsync` do arquivo de log confirme várias transações pequenas e concorrentes, e é assim que ele mantém a durabilidade viável sob carga.

</ArticleSection>

<ArticleSection id="implementation-examples">

Esta é a transferência como uma transação no PostgreSQL. A constraint `CHECK` põe uma das regras do banco no papel, para que o banco de dados possa impô-la:

```sql
ALTER TABLE accounts ADD CONSTRAINT balance_non_negative CHECK (balance >= 0);

BEGIN;
UPDATE accounts SET balance = balance - 100.00 WHERE name = 'Alice';
UPDATE accounts SET balance = balance + 100.00 WHERE name = 'Bob';
COMMIT;
```

Se Alice tiver menos de 100, o primeiro `UPDATE` viola a constraint, a transação é abortada e o `COMMIT` a encerra sem aplicar nada.

Com isolamento serializable, a aplicação repete a transação diante de uma falha de serialização, que o PostgreSQL informa com o SQLSTATE `40001`. Com o driver `psycopg`, o laço de retry fica assim:

```python
import psycopg
from psycopg import errors

def transfer(conn: psycopg.Connection, source: str, target: str, amount: int) -> None:
    conn.isolation_level = psycopg.IsolationLevel.SERIALIZABLE
    for _ in range(3):
        try:
            with conn.transaction():  # commit em caso de sucesso, rollback em caso de exceção
                conn.execute("UPDATE accounts SET balance = balance - %s WHERE name = %s", (amount, source))
                conn.execute("UPDATE accounts SET balance = balance + %s WHERE name = %s", (amount, target))
            return
        except errors.SerializationFailure:
            continue  # repete a transação inteira desde o início
    raise RuntimeError("transfer failed after 3 attempts")
```

<ArticleSection id="common-misconceptions">

- **"ACID significa que meus dados estão sempre corretos."** A consistência do ACID depende de invariantes definidas pela aplicação. O banco de dados só impõe as constraints que recebeu.
- **"O C de ACID é o C do teorema CAP."** Eles não têm relação. Em ACID significa preservar invariantes; em CAP refere-se a uma propriedade de dados replicados.
- **"Atômico significa thread-safe."** Em ACID, atomicidade trata de abortar de forma limpa depois de uma falha. A proteção contra acesso concorrente é o isolamento.
- **"Uma transação me dá isolamento serializable."** A maioria dos bancos de dados adota por padrão um nível mais fraco, como read committed, no qual podem ocorrer lost updates e outras anomalias.
- **"Durável significa que os dados nunca se perdem."** A durabilidade cobre a queda do processo ou da máquina. Ela não cobre um disco destruído sem backups nem réplicas.
- **"Bancos NoSQL não são ACID e bancos SQL são."** As garantias variam conforme o produto e a configuração, dos dois lados.

</ArticleSection>
