---
title: "Eventual Consistency"
description: "Replicas that converge to the same state once updates stop arriving."
---

<ArticleSection id="overview">

Remember the restaurant from the CAP theorem, the one with a front desk at each entrance? Give it a third desk, and let each host keep their own copy of the reservation book. When a host takes a booking, they write it down and send a note to the other two desks.

The notes take a moment to arrive, and sometimes a host is on a break when one comes in. For a while, a guest asking at one desk can get a different answer than at another. But if bookings stop for long enough, all three books end up the same. That promise has a name: **eventual consistency**.

In technical terms, it is a guarantee offered by replicated storage systems: <Mark variant="highlight" tone="brand">if no new updates are made to an item, all reads will eventually return the last written value</Mark>. Until then, different replicas, the copies kept on different machines, may answer the same question differently.

It exists because the alternative is expensive. Making every replica agree before acknowledging a write adds latency and makes the write fail whenever a replica is unreachable. Eventual consistency drops that requirement: a write is acknowledged once a subset of replicas has it, and the rest catch up in the background.

The period between a write and the moment every reader is guaranteed to see it is called the <Mark variant="underline" tone="teal">**inconsistency window**</Mark>. In the restaurant, it is the time a note spends on its way to the other desks.

<Callout type="info">
Werner Vogels, who popularized the term, describes eventual consistency as a specific form of weak consistency. The definition promises convergence, not a deadline.
</Callout>

</ArticleSection>

<ArticleSection id="how-it-works">

An eventually consistent store needs three things: a way to spread updates, a way to notice replicas that missed them, and a rule for deciding between conflicting versions.

**Propagation and repair.** Systems in the Dynamo family, such as Apache Cassandra, combine several mechanisms. Each one has a counterpart at the restaurant:

- **Hinted handoff:** when a replica is down, another node stores the write with a hint and delivers it once the replica returns. The note waits on the desk until the host is back from their break.
- **Read repair:** when a read finds replicas holding stale versions, the coordinator updates them. A host who notices an outdated entry while checking a booking fixes it on the spot.
- **Anti-entropy:** replicas periodically compare Merkle trees (hash trees) of their data and synchronize only the ranges that differ. At closing time, the hosts compare their books and copy only the pages that do not match. In Cassandra, <Mark variant="highlight" tone="amber">anti-entropy is the mechanism that actually guarantees convergence</Mark>; hints and read repair are best-effort.
- **Gossip:** nodes exchange membership and health information with random peers.

**Conflict resolution.** Two clients can update the same item on different replicas before those replicas communicate, just as two desks can book table 5 for different guests before their notes cross. Dynamo tracks causality with **vector clocks**: if neither version descends from the other, both are returned to the application, which merges them.

A simpler rule is <Mark variant="underline" tone="brand">**last write wins** (LWW)</Mark>: each write carries a timestamp and the highest one is kept. Here the analogy needs a warning. A real host would call the guest who lost the table; LWW drops the losing write silently. And the hosts share one wall clock, while servers each have their own, and those clocks drift apart.

**Quorums.** With `N` replicas, a write waits for `W` acknowledgements and a read queries `R` replicas. When `W + R > N`, the read set and the write set always overlap, so a read meets at least one replica with the latest write. When `W + R <= N` they may not overlap, and reads can be stale.

**Client-side guarantees.** Stronger variants limit what a single client can observe: *read-your-writes* (a process always sees its own updates), *monotonic reads* (a process never sees an older value than one it already saw) and *session consistency* (read-your-writes within a session).

</ArticleSection>

<ArticleSection id="when-to-use">

Eventual consistency fits when taking the booking now matters more than every desk agreeing right away:

- **Availability matters more than freshness.** The original Dynamo requirement was an "always writeable" store: adding an item to a shopping cart must succeed even during failures.
- **Data is replicated across regions** and waiting for a distant replica on every write would be too slow.
- **Read-heavy workloads** where many replicas serve reads and a slightly old answer is acceptable: catalogs, profiles, counters, feeds, name resolution.
- **Updates merge naturally**, for example adding elements to a set, so concurrent writes can be reconciled without losing intent.

</ArticleSection>

<ArticleSection id="when-not-to-use">

The trouble starts when a stale or lost write is not just awkward but wrong:

- **Invariants that must hold at every instant**, such as "a balance never goes below zero" or "a username is unique". <Mark variant="highlight" tone="amber">Two replicas can each accept a write that is valid locally and invalid together.</Mark>
- **Flows that read immediately after writing** and break on stale data, unless you can use a session guarantee or a strongly consistent read for those requests.
- **Data where silently discarding a concurrent write is unacceptable** and you have no merge logic. Last write wins will keep one version and drop the other.
- **Systems that fit a single database node or a single leader.** If you do not need multi-node write availability, you are paying the complexity for nothing.

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Advantages**

- Writes and reads stay available when some replicas or network links are down.
- Lower latency, because requests do not wait for every replica.
- Scales reads by adding replicas, and supports geographically distributed deployments.

**Disadvantages**

- Applications must tolerate stale reads and values that appear to go backwards.
- Conflict handling becomes application logic, and it is hard to test because the anomalies depend on timing.
- The inconsistency window has no fixed upper bound; it depends on communication delays, load and the number of replicas.
- Last write wins depends on timestamps, so clock skew between nodes can pick the wrong winner.

</ArticleSection>

The `N`, `W` and `R` values are the main dial. Vogels describes the common configurations, compared here for three replicas:

Other costs to weigh:

- **Money and latency versus freshness.** In DynamoDB, an eventually consistent read costs half as much as a strongly consistent one.
- **Simplicity versus correctness of merges.** Last write wins is trivial to operate but loses concurrent updates; application-level merging preserves them and adds code to every read path.
- **Background work.** Anti-entropy consumes I/O and CPU, but skipping it lets replicas drift indefinitely.

</ArticleSection>

<ArticleSection id="real-world-examples">

- **DNS.** Vogels cites the Domain Name System as the most popular eventually consistent system: updates are distributed according to a configured pattern and combined with time-controlled caches, so all clients eventually see a change.
- **Amazon Dynamo.** The 2007 paper describes the store behind Amazon's shopping cart. Many instances used `(N, R, W) = (3, 2, 2)`. Divergent carts are merged by the application, so an added item is never lost, but a deleted item can resurface.
- **Apache Cassandra.** Consistency is tunable per operation with levels such as `ONE`, `QUORUM` and `ALL`. Conflicts are resolved by last write wins on timestamps, which is why the documentation recommends running a time synchronization service such as NTP.
- **Amazon DynamoDB.** Reads are eventually consistent by default; `ConsistentRead` opts into strong consistency on tables and local secondary indexes. Reads from global secondary indexes and streams are always eventually consistent.

</ArticleSection>

<ArticleSection id="implementation-examples">

In DynamoDB you choose the consistency level per request. With the AWS SDK for JavaScript v3, a product listing can take the cheap read and the checkout the strong one:

```ts
import { DynamoDBClient, GetItemCommand } from '@aws-sdk/client-dynamodb'

const client = new DynamoDBClient({})
const key = { productId: { S: 'sku-123' } }

// Default: eventually consistent. May not reflect a write that just completed.
const listing = await client.send(new GetItemCommand({ TableName: 'Products', Key: key }))

// Strongly consistent: reflects all prior successful writes.
const checkout = await client.send(
  new GetItemCommand({ TableName: 'Products', Key: key, ConsistentRead: true }),
)
```

Next, a last-write-wins merge, the rule replicas apply when they exchange versions. Because the function is deterministic and does not depend on the order of its arguments, every replica that sees both versions picks the same winner:

```ts
type Versioned<T> = { value: T; timestamp: number; nodeId: string }

function mergeLww<T>(a: Versioned<T>, b: Versioned<T>): Versioned<T> {
  if (a.timestamp !== b.timestamp) return a.timestamp > b.timestamp ? a : b
  return a.nodeId > b.nodeId ? a : b // deterministic tie-break
}
```

<Callout type="warning">
`mergeLww` converges, but the losing write is discarded without notice. Use it only when overwriting a concurrent update is acceptable.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"Eventually means within a few milliseconds."** It often is that fast, but the definition sets no bound. A replica that was down for an hour is an hour behind when it returns.
- **"Converged means correct."** Convergence only says replicas agree. Whether the agreed value preserves every user's intent depends on the conflict resolution rule.
- **"It is a property of the whole database."** In Dynamo-style stores and in DynamoDB the level is chosen per request, so one application can mix eventual and strong reads.
- **"A quorum makes the system strongly consistent in every case."** `W + R > N` guarantees overlap only if reads and writes use the same set of `N` replicas. A sloppy quorum, which accepts writes on stand-in nodes during failures, trades that guarantee for availability.
- **"Eventual consistency means no guarantees."** Read-your-writes, monotonic reads and session consistency can be layered on top, and they remove the anomalies users notice most.

</ArticleSection>
