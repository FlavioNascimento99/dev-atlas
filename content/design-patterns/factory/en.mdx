---
title: "Factory"
description: "Delegating object creation to a dedicated method or object."
---

<ArticleSection id="overview">

Think about renting a car. You don't walk into the lot and pick a specific vehicle by its serial number. You go to the counter and ask for "a compact car". The agency decides which one you get, prepares the paperwork and hands you the keys.

You don't mind which model it is, because every car works the same from the driver's seat: steering wheel, pedals, gear stick. You know *what kind* of thing you need, not *which exact one*.

In code, that counter is a **factory**: any function, method or object whose job is to create other objects. Instead of writing `new ConcreteClass()` wherever an object is needed, client code asks the factory for <Mark variant="highlight" tone="brand">"something that satisfies this interface"</Mark> and lets it decide which class to instantiate and how.

The problem it solves is <Mark variant="underline" tone="brand">coupling to concrete classes</Mark>. A constructor call names an exact class. So every place that creates an object must know which variant to build and with which arguments, and it must change whenever a new variant appears. Putting that decision in one place lets the rest of the code depend only on an abstraction.

"Factory" is an umbrella term. The catalog by Gamma, Helm, Johnson and Vlissides — the "Gang of Four" (GoF) — describes two specific creational patterns, **Factory Method** and **Abstract Factory**. Everyday code also uses lighter forms that are not GoF patterns, such as a static creation method or a simple factory function.

</ArticleSection>

<ArticleSection id="how-it-works">

Every variant makes the same move as the rental counter. The client calls a creation operation and gets back a **product**, the object being created, typed as an interface. The client never names the concrete class, just as you never name the car's serial number.

What changes from one variant to another is *where* the choice of class happens. The table lists the forms you will meet:

/>

**Factory Method** has four participants:

- The **product** is the interface of the objects being created — "a compact car". **Concrete products** implement it, like each actual model.
- The **creator** is a class that declares the factory method. Here the analogy needs a correction: the creator is not just a counter that hands things out. <Mark variant="highlight" tone="teal">It contains business logic that *uses* the product it returns</Mark>, the way a rental process always runs the same paperwork, whatever car comes out.
- **Concrete creators** override the factory method to return a specific product, like two branches of the agency with different fleets.

Because the creator's own logic calls a step that subclasses can override, Factory Method is a specialization of the <Mark variant="underline" tone="teal">Template Method</Mark> pattern.

**Abstract Factory** raises the idea one level. Imagine asking the agency for a car *and* a matching child seat *and* a roof box, all guaranteed to fit together. The factory itself is an interface with one creation method per kind of product, and swapping the concrete factory swaps the whole family at once. Its methods are often implemented as factory methods.

</ArticleSection>

<ArticleSection id="when-to-use">

A factory pays off when the code that needs an object shouldn't be the one deciding which object it is. Typical cases:

- **The concrete type is not known where the object is needed.** It depends on configuration, input, platform or locale.
- **A library or framework must let its users supply their own components.** The framework calls a factory method; users override it.
- **Construction logic is non-trivial and repeated.** Validation, default values and wiring belong in one place.
- **A constructor cannot express what you need.** A creation method can have a descriptive name, return an existing instance from a cache or pool, or return a subtype.
- **Groups of objects must be consistent with each other.** Use an Abstract Factory so that mixing families becomes impossible.

</ArticleSection>

<ArticleSection id="when-not-to-use">

If there is only one car in the lot, the counter is just a detour. Skip the factory when:

- **There is one concrete class and no sign of a second.** A constructor call is clearer, and <Mark variant="highlight" tone="amber">the factory can be introduced later by refactoring</Mark>.
- **Construction is trivial.** Wrapping `new Point(x, y)` in a factory adds a hop and no information.
- **The variation is in data, not in type.** If the "products" differ only in field values, pass parameters instead of creating a class hierarchy.
- **A dependency injection container already wires the objects.** Adding hand-written factories on top often duplicates what the container does.

<Callout type="warning">
Factory Method requires a creator subclass for every product. If creation is the only thing those subclasses do, a simple factory function achieves the same decoupling with far fewer classes.
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Advantages**

- Client code depends on an interface, not on concrete classes.
- Creation logic lives in one place, which is easier to maintain and test.
- New product types are added without modifying existing client code.
- The factory controls instances: it can reuse, cache or pool them instead of always allocating.

**Disadvantages**

- More classes and indirection; reading the code means jumping from the call site to the factory to the product.
- Factory Method ties creation to an inheritance hierarchy that may exist only for that purpose.
- With Abstract Factory, adding a new *kind* of product means changing the factory interface and every concrete factory.
- The concrete type is hidden, which is the point, but it can make debugging less direct.

</ArticleSection>

<ArticleSection id="trade-offs">

The choice is between **flexibility at the point of creation and directness**. <Mark variant="highlight" tone="brand">Every factory is a bet that the set of concrete classes will change.</Mark> When the bet is right, a new variant is a local addition. When it is wrong, the indirection is pure cost.

Among the variants, the trade is **power for ceremony**:

- A creation method costs one function.
- A simple factory centralizes a conditional, but that conditional must be edited for every new product.
- Factory Method removes the conditional by moving the choice into subclasses, at the price of a parallel class hierarchy.
- Abstract Factory guarantees consistent families and makes a new family easy to add, but a new product kind hard.

Designs often start at the cheap end and move along that scale only as real variation appears.

</ArticleSection>

<ArticleSection id="real-world-examples">

You have probably used factories without noticing. A few well-known ones:

- **`java.util.Calendar`.** The class is abstract with protected constructors, so you can't call `new Calendar()`. You obtain one through `Calendar.getInstance()`, whose overloads accept a time zone and a locale. Client code works with the `Calendar` type without naming a subclass.
- **`java.util.List.of` and `List.copyOf`.** The Java documentation calls these static factory methods and states that callers should make no assumptions about the identity of the returned instances: the factories are free to create new instances or reuse existing ones. `copyOf` on a list that is already unmodifiable generally does not create a copy — an optimization a public constructor could not offer.
- **Refactoring catalog.** Martin Fowler lists *Replace Constructor with Factory Function* as a standard refactoring, turning `new Employee(name, 'E')` into `createEngineer(name)`.

</ArticleSection>

<ArticleSection id="implementation-examples">

Start with the simplest form: a simple factory in TypeScript. The union type makes the compiler reject unknown formats, and the `switch` is the single place that knows the concrete classes:

```ts
interface Writer {
  write(text: string): string
}

class PdfWriter implements Writer {
  write(text: string) {
    return `%PDF ${text}`
  }
}

class HtmlWriter implements Writer {
  write(text: string) {
    return `<p>${text}</p>`
  }
}

type Format = 'pdf' | 'html'

export function createWriter(format: Format): Writer {
  switch (format) {
    case 'pdf':
      return new PdfWriter()
    case 'html':
      return new HtmlWriter()
  }
}
```

The same products behind a GoF Factory Method. `save` is business logic written once against the abstraction; subclasses only say what to create:

```ts
abstract class Exporter {
  protected abstract createWriter(): Writer // the factory method

  save(text: string): string {
    const writer = this.createWriter()
    return writer.write(text.trim())
  }
}

class PdfExporter extends Exporter {
  protected createWriter(): Writer {
    return new PdfWriter()
  }
}

class HtmlExporter extends Exporter {
  protected createWriter(): Writer {
    return new HtmlWriter()
  }
}

const exporter: Exporter = new PdfExporter()
exporter.save(' hello ') // "%PDF hello"
```

<Callout type="tip">
In languages with first-class functions, a factory can simply be a function passed as an argument, such as `() => new PdfWriter()`. That gives the creator the same freedom without a subclass per product.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

The word "factory" is used loosely, so a few mix-ups are common:

- **"Factory is one of the GoF patterns."** The book defines Factory Method and Abstract Factory. "Factory" alone is a loose term whose meaning depends on context.
- **"A static creation method is the Factory Method pattern."** Factory Method relies on subclasses overriding the creation step; a static method cannot be overridden. Static creation methods are useful, but they are a different, simpler idiom.
- **"A simple factory declared abstract is an Abstract Factory."** Abstract Factory is about producing *families* of related products through several creation methods, not about the `abstract` keyword.
- **"A factory always returns a new object."** The rental agency doesn't build a car for you; it hands over one from the lot. Likewise, <Mark variant="underline" tone="amber">a factory may return a cached or shared instance</Mark>, as the Java collection factories explicitly reserve the right to do.
- **"The creator's job is to create."** In Factory Method, the creator's main responsibility is the logic that uses the product. The factory method exists so that logic does not depend on a concrete class.

</ArticleSection>
