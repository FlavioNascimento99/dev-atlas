title: "Como funcionam os load balancers"
description: "Distribuição de requisições entre servidores para aumentar vazão e disponibilidade."
---

<ArticleSection id="overview">

Pense num supermercado lotado num sábado. Há dez caixas abertos e um funcionário no fim dos corredores organizando a fila: "caixa 4 livre!". Ninguém precisa escolher fila e, quando uma operadora sai para o intervalo, ele simplesmente para de mandar gente para lá.

Um **load balancer** é esse funcionário. Ele <Mark variant="highlight" tone="brand">fica entre os clientes e um grupo de servidores capazes de fazer o mesmo trabalho</Mark>. Ele recebe cada requisição ou conexão e decide qual servidor, normalmente chamado de *backend* ou *target*, vai atendê-la.

Ele resolve dois problemas de uma vez. Um servidor tem um teto de tráfego que consegue atender, então a capacidade precisa crescer com a adição de máquinas, e algo precisa repartir o tráfego entre elas.

Além disso, qualquer máquina acaba falhando ou precisando de manutenção, então algo precisa parar de enviar tráfego a ela sem que os clientes percebam. O load balancer dá ao grupo inteiro <Mark variant="underline" tone="teal">um endereço estável</Mark> e esconde quais máquinas estão por trás dele, do mesmo jeito que o cliente entra no supermercado, e não no caixa 4.

</ArticleSection>

<ArticleSection id="how-it-works">

Um load balancer combina quatro mecanismos.

**Um ponto de entrada estável.** Os clientes se conectam a um único endereço, a porta da loja. No nível de rede, ele costuma ser um *endereço IP virtual*: um endereço que não está preso a uma única interface de rede e pode ser atendido por vários dispositivos, parecendo um só endpoint para quem está de fora.

**Um pool de backends.** A lista de servidores aptos a receber tráfego, os caixas abertos. Ela muda conforme máquinas são adicionadas, removidas ou substituídas, idealmente sem interromper as requisições em andamento.

**Health checks.** O balanceador <Mark variant="underline" tone="brand">só encaminha para backends que considera saudáveis</Mark>, como quem pula o caixa com a maquininha de cartão quebrada. Checagens *ativas* sondam cada servidor periodicamente; checagens *passivas* observam o tráfego real e tiram um servidor da rotação depois de falhas repetidas. No NGINX, por exemplo, um servidor é considerado indisponível por `fail_timeout` (10 segundos por padrão) depois de `max_fails` tentativas com falha (1 por padrão).

**Um algoritmo de seleção.** Para cada requisição, escolher um backend saudável. É a regra que o funcionário do fim dos corredores segue:

- **Round robin** percorre a lista em ordem, opcionalmente com pesos para que máquinas maiores recebam proporcionalmente mais. Caixa 1, caixa 2, caixa 3 e de volta ao caixa 1.
- **Least connections** escolhe o backend com menos conexões ativas, adaptando-se a requisições de duração desigual. Mandar o cliente para a fila mais curta.
- **Random** escolhe um backend qualquer. A variante *power of two choices* sorteia dois e fica com o menos carregado.
- **Hashing** mapeia uma chave, como o IP do cliente, para um backend, de modo que o mesmo cliente continue chegando ao mesmo servidor. O *consistent hashing* mantém a maior parte desses mapeamentos estável quando um backend entra ou sai, enquanto um simples `hash mod N` remapeia quase tudo.

Os balanceadores também diferem na camada em que operam. Um balanceador de **camada 4** encaminha pacotes TCP ou UDP sem interpretá-los, o que é barato e independente de protocolo. Um balanceador de **camada 7** termina a conexão, interpreta o HTTP e pode rotear por caminho, cabeçalho ou cookie, terminar TLS e repetir requisições que falharam, a um custo maior por requisição.

Na língua do supermercado, a camada 4 aponta um caixa sem olhar o seu carrinho. A camada 7 vê o que você está levando e pode mandar você para o caixa rápido ou para o balcão da farmácia.

</ArticleSection>

<ArticleSection id="when-to-use">

Você precisa de alguém organizando a fila assim que existe mais de um caixa:

- **Há mais de uma instância de um serviço** em execução, por capacidade ou por redundância.
- **Os deploys não podem causar indisponibilidade**: as instâncias são drenadas, substituídas e recolocadas atrás do mesmo endereço.
- **As instâncias aparecem e somem automaticamente**, como em grupos de autoscaling ou orquestradores de containers.
- **Trabalho transversal deve sair da aplicação**: terminação de TLS, reaproveitamento de conexões, roteamento por host ou caminho.
- **O tráfego precisa sobreviver à perda de uma máquina ou de uma zona**, distribuindo os targets entre domínios de falha.

</ArticleSection>

<ArticleSection id="when-not-to-use">

Um mercadinho com um caixa só não precisa de ninguém organizando fila. Nem estes casos:

- **Uma única instância basta** e uma breve indisponibilidade é aceitável. Um balanceador na frente de um só servidor acrescenta um salto e um componente sem acrescentar disponibilidade.
- **O gargalo está em outro lugar.** Se todas as instâncias esperam pelo mesmo banco de dados saturado, distribuir requisições entre mais instâncias não ajuda.
- **O estado vive na instância.** Sessões em memória ou arquivos locais obrigam o cliente a voltar ao mesmo servidor; mova esse estado para um armazenamento compartilhado antes de depender de um balanceador.
- **O trabalho não tem formato de requisição.** Jobs longos em segundo plano costumam ser mais bem distribuídos por uma fila, da qual os workers puxam, do que empurrados por um balanceador.

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Vantagens**

- Escala horizontal: a capacidade cresce com a adição de backends.
- Maior disponibilidade: backends não saudáveis deixam de receber tráfego.
- Flexibilidade operacional: deploys graduais, drenagem e manutenção sem mudar o endereço usado pelos clientes.
- Um único lugar para TLS, regras de roteamento e métricas de tráfego.

**Desvantagens**

- <Mark variant="underline" tone="amber">O próprio balanceador é um possível ponto único de falha</Mark> e precisa ser redundante.
- Um salto de rede a mais e, na camada 7, processamento adicional por requisição.
- Health checks podem errar nos dois sentidos: uma checagem superficial mantém um servidor quebrado na rotação, e uma rígida demais remove capacidade saudável.
- Carga desigual continua possível, porque o balanceador enxerga conexões ou contagens de requisições, e não o custo real de cada requisição.

Aqui a analogia do supermercado é mais generosa que a realidade. O funcionário do fim dos corredores consegue bater o olho e ver se o carrinho está cheio. Um load balancer normalmente não consegue: ele conta requisições ou conexões, não quanto trabalho cada uma vai dar.

</ArticleSection>

**Camada 4 ou camada 7.** A camada 4 é mais rápida e serve para qualquer protocolo, mas não consegue rotear pelo conteúdo. A camada 7 entende as requisições e paga por isso em CPU e na posse das chaves TLS.

**Sessões fixas ou ausência de estado.** A persistência de sessão faz aplicações com estado funcionarem sem alterações, mas prejudica a distribuição uniforme e perde sessões quando um backend desaparece.

**Encaminhamento com ou sem estado.** Rastrear cada conexão garante que seus pacotes cheguem ao mesmo backend, mas a tabela custa memória e pode se esgotar sob ataque. O hashing dispensa a tabela, mas remapeia conexões quando o pool muda. Sistemas grandes combinam os dois.

<Callout type="warning">
Least connections pode transformar um servidor quebrado em um sumidouro: ele responde com erros quase instantaneamente, então sempre tem menos requisições ativas e recebe uma fatia crescente do tráfego. Conte erros recentes como carga ou remova servidores com falha por meio de health checks.
</Callout>

Imagine um caixa cuja maquininha recusa todo pagamento em um segundo. A fila dele está sempre mais curta, então a regra "mande para a fila mais curta" continua mandando gente para lá. <Mark variant="highlight" tone="brand">Fila vazia não é o mesmo que caixa funcionando.</Mark>

</ArticleSection>

<ArticleSection id="real-world-examples">

- O **Google Maglev** é um load balancer de rede em software que roda em servidores Linux comuns. Segundo o artigo de 2016, ele atende o tráfego do Google desde 2008: roteadores espalham os pacotes entre as máquinas Maglev com ECMP, e cada máquina usa consistent hashing e rastreamento de conexões para escolher um backend.
- O **balanceamento de RPC nos datacenters do Google**, descrito no livro de SRE, constatou que o round robin simples deixava uma diferença de cerca de duas vezes no uso de CPU entre as tarefas menos e mais carregadas. O weighted round robin, alimentado por informações de carga reportadas pelos backends, reduziu essa diferença.
- O **AWS Elastic Load Balancing** distribui o tráfego entre targets como instâncias EC2, containers e endereços IP em uma ou mais Availability Zones, encaminha apenas para targets que passam nos health checks e oferece Application, Network e Gateway Load Balancers.
- O **NGINX** é muito usado como load balancer HTTP; seu método padrão é o weighted round robin, com least connections, hashing e seleção aleatória disponíveis como diretivas.

</ArticleSection>

<ArticleSection id="implementation-examples">

Esta é uma configuração do NGINX que balanceia tráfego HTTP com least connections, um servidor com peso e um de backup:

```nginx
upstream api {
    least_conn;
    server 10.0.0.11:8080 weight=2;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 backup;
}

server {
    listen 80;
    location / {
        proxy_pass http://api;
    }
}
```

Trocar `least_conn;` por `random two least_conn;` ativa o power of two choices, e `hash $request_uri consistent;` ativa o consistent hashing sobre a URI.

Os dois algoritmos mais simples cabem em poucas linhas de TypeScript. O round robin só lembra uma posição; o least connections compara todos os backends:

```typescript
type Backend = { address: string; activeConnections: number }

function roundRobin(backends: Backend[]): () => Backend {
  let cursor = 0
  return () => backends[cursor++ % backends.length]
}

function leastConnections(backends: Backend[]): Backend {
  return backends.reduce((best, current) =>
    current.activeConnections < best.activeConnections ? current : best,
  )
}
```

<ArticleSection id="common-misconceptions">

- **"Round robin distribui a carga de forma uniforme."** Ele distribui as *requisições* de forma uniforme. A carga depende do custo de cada requisição e do que mais cada máquina está fazendo.
- **"Um load balancer torna o sistema altamente disponível."** Só se o próprio balanceador for redundante e os backends não compartilharem um ponto único de falha atrás dele.
- **"DNS com vários registros é um load balancer."** Ele espalha os clientes, mas o operador tem pouco controle: os clientes escolhem entre os registros arbitrariamente, os resolvedores guardam as respostas em cache e as mudanças demoram a surtir efeito.
- **"O health check passou, então o servidor está bem."** Uma checagem que só testa se a porta está aberta não diz nada sobre o sucesso das requisições reais.
- **"Sticky sessions são inofensivas."** Elas amarram o destino de um usuário a uma máquina e dificultam drenar ou rebalancear servidores.

</ArticleSection>
