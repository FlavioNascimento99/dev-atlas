title: "How Load Balancers Work"
description: "Distributing requests across servers to improve throughput and availability."

<ArticleSection id="overview">

Think of a busy supermarket on a Saturday. There are ten checkouts, and someone at the end of the aisles points each shopper to a lane: "number 4 is free". Nobody has to pick a line, and when a cashier goes on a break, shoppers simply stop being sent there.

A **load balancer** is that person. It <Mark variant="highlight" tone="brand">sits between clients and a group of servers that can all do the same job</Mark>. It receives each request or connection and decides which server, usually called a *backend* or *target*, will handle it.

It solves two problems at once. One server has a ceiling on how much traffic it can serve, so capacity has to grow by adding machines, and something must spread the traffic among them.

And any single machine eventually fails or needs maintenance, so something must stop sending traffic to it without clients noticing. The load balancer gives the whole group <Mark variant="underline" tone="teal">one stable address</Mark> and hides which machines are behind it, just as shoppers walk into one store, not into lane 4.

</ArticleSection>

<ArticleSection id="how-it-works">

A load balancer combines four mechanisms.

**A stable entry point.** Clients connect to one address, the store's front door. At the network level this is often a *virtual IP address*: an address that is not tied to a single network interface and can be served by many devices while looking like one endpoint to the outside.

**A pool of backends.** The list of servers eligible for traffic, the checkouts that are open. It changes as machines are added, removed or replaced, ideally without interrupting requests in flight.

**Health checking.** The balancer <Mark variant="underline" tone="brand">only routes to backends it believes are healthy</Mark>, like skipping a lane whose card machine is down. *Active* checks probe each server periodically; *passive* checks watch real traffic and take a server out of rotation after repeated failures. In NGINX, for example, a server is considered unavailable for `fail_timeout` (10 seconds by default) after `max_fails` failed attempts (1 by default).

**A selection algorithm.** For each request, pick one healthy backend. This is the rule the person at the end of the aisles follows:

- **Round robin** rotates through the list in order, optionally with weights so larger machines receive proportionally more. Lane 1, lane 2, lane 3, and back to lane 1.
- **Least connections** picks the backend with the fewest active connections, adapting to requests of uneven duration. Send the shopper to the shortest line.
- **Random** picks any backend. The *power of two choices* variant picks two at random and keeps the less loaded one.
- **Hashing** maps a key such as the client IP to a backend, so the same client keeps reaching the same server. *Consistent hashing* keeps most of those mappings stable when a backend joins or leaves, whereas a plain `hash mod N` remaps almost everything.

Balancers also differ in the layer where they operate. A **layer 4** balancer forwards TCP or UDP packets without interpreting them, which is cheap and protocol-agnostic. A **layer 7** balancer terminates the connection, parses HTTP and can route by path, header or cookie, terminate TLS and retry failed requests, at a higher cost per request.

In supermarket terms, layer 4 points you to a lane without looking in your cart. Layer 7 checks what you are carrying and can send you to the express lane or the pharmacy counter.

</ArticleSection>

<ArticleSection id="when-to-use">

You need someone pointing to lanes as soon as there is more than one lane:

- **More than one instance of a service** is running, for capacity or for redundancy.
- **Deployments must not cause downtime**: instances are drained, replaced and added back behind the same address.
- **Instances come and go automatically**, as with autoscaling groups or container orchestrators.
- **Cross-cutting work should leave the application**: TLS termination, connection reuse, request routing by host or path.
- **Traffic must survive the loss of a machine or a zone**, by spreading targets across failure domains.

</ArticleSection>

<ArticleSection id="when-not-to-use">

A store with one checkout does not need anyone directing traffic. Nor do these cases:

- **A single instance is enough** and brief downtime is acceptable. A balancer in front of one server adds a hop and a component without adding availability.
- **The bottleneck is elsewhere.** If every instance waits on the same saturated database, distributing requests among more instances does not help.
- **State lives in the instance.** In-memory sessions or local files force clients back to the same server; move that state to a shared store before relying on a balancer.
- **Work is not request-shaped.** Long background jobs are usually better distributed through a queue that workers pull from than pushed through a balancer.

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Advantages**

- Horizontal scaling: capacity grows by adding backends.
- Higher availability: unhealthy backends stop receiving traffic.
- Operational flexibility: rolling deployments, draining and maintenance without changing the address clients use.
- A single place for TLS, routing rules and traffic metrics.

**Disadvantages**

- <Mark variant="underline" tone="amber">The balancer is itself a potential single point of failure</Mark> and must be made redundant.
- An extra network hop and, at layer 7, extra processing per request.
- Health checks can be wrong in both directions: a shallow check keeps a broken server in rotation, an overly strict one removes healthy capacity.
- Uneven load is still possible, because the balancer sees connections or request counts and not the true cost of each request.

Here the supermarket analogy is kinder than reality. A person at the end of the aisles can glance at how full each cart is. A load balancer usually cannot: it counts requests or connections, not how much work each one will take.

</ArticleSection>

Each selection algorithm trades how much it needs to know for how evenly it spreads the work. The table puts them side by side:

  rows={[
    ["Round robin", "A position in the list", "Requests cost about the same and servers are alike", "Ignores how busy each server is"],
    ["Least connections", "Active connections per server", "Request duration varies widely", "A server failing fast looks idle and attracts traffic"],
    ["Random (two choices)", "Load of two sampled servers", "A cheap approximation of least connections is enough", "Slightly less even than a full comparison"],
    ["Hash of a key", "None per request", "Requests should stick to a server", "Hot keys overload one server"],
  ]}
/>

**Layer 4 or layer 7.** Layer 4 is faster and works for any protocol but cannot route on content. Layer 7 understands requests and pays for it in CPU and in owning the TLS keys.

**Stickiness or statelessness.** Session persistence makes stateful applications work unchanged, but it defeats even distribution and loses sessions when a backend disappears.

**Stateful or stateless forwarding.** Tracking every connection guarantees that its packets reach the same backend, but the table costs memory and can be exhausted under attack. Hashing needs no table but remaps connections when the pool changes. Large systems combine both.

<Callout type="warning">
Least connections can turn a broken server into a sinkhole: it answers with errors almost instantly, so it always has the fewest active requests and receives a growing share of traffic. Count recent errors as load, or eject failing servers through health checks.
</Callout>

Picture a checkout where the card machine rejects every payment in a second. Its line is always the shortest, so a "shortest line" rule keeps sending shoppers there. <Mark variant="highlight" tone="brand">An empty line is not the same as a working lane.</Mark>

</ArticleSection>

<ArticleSection id="real-world-examples">

- **Google Maglev** is a software network load balancer running on commodity Linux servers. According to its 2016 paper it has served Google's traffic since 2008: routers spread packets across Maglev machines with ECMP, and each machine uses consistent hashing and connection tracking to choose a backend.
- **Google's datacenter RPC balancing**, described in the SRE book, found that simple round robin left roughly a twofold spread in CPU usage between the least and the most loaded tasks. Weighted round robin, fed by load information reported by the backends, narrowed that spread.
- **AWS Elastic Load Balancing** distributes traffic across targets such as EC2 instances, containers and IP addresses in one or more Availability Zones, routes only to targets that pass health checks, and offers Application, Network and Gateway Load Balancers.
- **NGINX** is widely used as an HTTP load balancer; its default method is weighted round robin, with least connections, hashing and random selection available as directives.

</ArticleSection>

<ArticleSection id="implementation-examples">

Here is an NGINX configuration that balances HTTP traffic with least connections, a weighted server and a backup:

```nginx
upstream api {
    least_conn;
    server 10.0.0.11:8080 weight=2;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 backup;
}

server {
    listen 80;
    location / {
        proxy_pass http://api;
    }
}
```

Replacing `least_conn;` with `random two least_conn;` switches to the power of two choices, and `hash $request_uri consistent;` switches to consistent hashing on the URI.

The two simplest algorithms fit in a few lines of TypeScript. Round robin only remembers a position; least connections compares every backend:

```typescript
type Backend = { address: string; activeConnections: number }

function roundRobin(backends: Backend[]): () => Backend {
  let cursor = 0
  return () => backends[cursor++ % backends.length]
}

function leastConnections(backends: Backend[]): Backend {
  return backends.reduce((best, current) =>
    current.activeConnections < best.activeConnections ? current : best,
  )
}
```

<ArticleSection id="common-misconceptions">

- **"Round robin distributes load evenly."** It distributes *requests* evenly. Load depends on what each request costs and on what else each machine is doing.
- **"A load balancer makes the system highly available."** Only if the balancer itself is redundant and the backends do not share a single failure point behind it.
- **"DNS with several records is a load balancer."** It spreads clients, but the operator has little control: clients choose among the records arbitrarily, resolvers cache answers and changes take effect slowly.
- **"The health check passes, so the server is fine."** A check that only tests whether a port is open says nothing about whether real requests succeed.
- **"Sticky sessions are harmless."** They tie a user's fate to one machine and make it harder to drain or rebalance servers.

</ArticleSection>
