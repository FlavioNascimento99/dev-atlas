<ArticleSection id="overview">

Pense em como você liga para alguém. Você não digita o número de cabeça. Você procura o nome na agenda do celular, e o aparelho encontra o número para você.

A internet funciona do mesmo jeito. Você digita `www.example.com`, mas o seu computador só sabe se conectar a um número: um **endereço IP**. Alguém precisa transformar o nome nesse número.

Esse alguém é o **Domain Name System (DNS)**, a <Mark variant="highlight" tone="brand">agenda de contatos da internet</Mark>. Ele mapeia nomes legíveis por pessoas para os dados necessários para alcançar um serviço — na maioria das vezes um endereço IP, mas também servidores de e-mail, aliases e texto livre. Programas conversam com endereços IP; pessoas e arquivos de configuração trabalham com nomes. O DNS é a camada de consulta que fica entre os dois.

Tem uma diferença grande em relação à agenda do seu celular: ninguém guarda a agenda inteira. O DNS é um <Mark variant="underline" tone="brand">banco de dados hierárquico e distribuído</Mark>. O espaço de nomes é uma árvore, e cada ramo pode ser entregue a um operador diferente, que passa a responder só pela sua parte.

Esse desenho resolve dois problemas de uma vez. Primeiro, **indireção**: um nome continua o mesmo enquanto as máquinas por trás dele mudam, como um contato que mantém o nome quando a pessoa troca de número. Segundo, **escala sem controle central**: nenhuma organização detém todos os dados.

</ArticleSection>

<ArticleSection id="how-it-works">

Imagine essa agenda rasgada em páginas, cada uma guardada por um dono diferente. Para achar um número, alguém precisa saber a qual dono perguntar. O DNS tem três tipos de participantes para isso:

- **Resolvers** fazem as perguntas. Um resolver recebe a pergunta de um programa e encontra a resposta em nome dele — é o assistente que sai procurando o número por você. O pequeno resolver dentro do sistema operacional (um *stub resolver*) normalmente repassa todas as perguntas a um **resolver recursivo**, operado por um provedor de internet, pela rede da empresa ou por um provedor público.
- **Name servers** guardam as páginas. Um servidor é **autoritativo** para uma **zona** — uma parte contígua do espaço de nomes pela qual ele é responsável. Espera-se que toda zona seja servida por pelo menos dois servidores, para redundância.
- **Resource records** são as entradas de cada página. Todo registro tem um nome, um tipo, um **TTL** (time to live, ou "tempo de vida") e um valor.

A árvore é dividida por <Mark variant="underline" tone="teal">delegação</Mark>: cada nível diz "essa entrada não está comigo, mas eu sei quem tem". A zona raiz delega `com` aos servidores desse domínio de topo (TLD). Esses servidores, por sua vez, delegam `example.com` aos servidores de quem o registrou.

As delegações são escritas como registros `NS`, colocados no ponto em que uma zona termina e outra começa.

Quando um resolver recursivo não tem nada em cache, ele percorre essa árvore a partir do topo. Pergunta a um servidor raiz e recebe uma *referência* (referral), que aponta para os servidores do TLD. Pergunta a um deles e recebe uma referência para os servidores autoritativos do domínio. Aí, finalmente, obtém a resposta.

E como ele sabe onde fica o topo? O resolver já vem com uma lista embutida dos nomes e endereços dos servidores raiz, os *root hints*.

Percorrer a árvore a cada consulta seria lento, então os resolvers guardam o que aprendem. Isso é o **cache**, parecido com salvar na agenda um número que você acabou de descobrir. Todo registro carrega um TTL, que diz por quanto tempo ele pode ficar em cache antes de ser descartado.

<Mark variant="highlight" tone="brand">O cache é o que torna o sistema rápido</Mark>: a maioria das perguntas é respondida da memória do resolver, sem tocar em nenhum servidor autoritativo. Até respostas do tipo "este nome não existe" podem ir para o cache, por um tempo derivado do registro `SOA` da zona.

Um nome pode apontar para mais coisas além de um endereço, por isso os registros têm tipos. Estes são os que você mais vai encontrar:

Por baixo dos panos, as consultas trafegam pela porta 53. O DNS clássico sobre UDP limita a mensagem a 512 bytes. Quando a resposta não cabe, o servidor liga a flag de truncamento (`TC`) e o cliente repete a consulta via TCP.

Os requisitos atuais tornam o suporte a TCP obrigatório para toda implementação de DNS de uso geral. Não é um fallback opcional.

</ArticleSection>

<ArticleSection id="when-to-use">

Se o seu software conversa com outra máquina, ele quase sempre deveria encontrá-la pelo nome. Na prática, o DNS é a ferramenta certa para:

- **Dar um nome estável a cada serviço.** Clientes devem usar `api.example.com`, nunca um endereço IP literal. Assim <Mark variant="highlight" tone="brand">a infraestrutura pode mudar sem um novo deploy dos clientes</Mark>.
- **Direcionamento grosseiro de tráfego.** Publicar endereços diferentes ou múltiplos para um nome é uma forma simples de distribuir clientes entre regiões ou provedores.
- **Delegar controle.** Você pode entregar um subdomínio a outro time ou fornecedor com registros `NS`, ou apontá-lo para um serviço de terceiros com um `CNAME`.
- **Publicar metadados do domínio**, como o roteamento de e-mail (`MX`) e declarações de propriedade ou de política (`TXT`).

</ArticleSection>

<ArticleSection id="when-not-to-use">

Aqui a comparação com a agenda do celular deixa de funcionar. Quando você edita um contato, o celular vê a mudança na hora. No DNS, cópias da entrada antiga ficam em caches que você não controla. Isso descarta alguns usos:

- **Failover rápido.** Depois que um registro muda, os caches continuam servindo o valor antigo até o TTL expirar, e você não controla os resolvers que o guardam. <Mark variant="highlight" tone="amber">O DNS sozinho não consegue tirar o tráfego de um host com falha em segundos.</Mark>
- **Balanceamento de carga por requisição.** Um resolver guarda uma resposta em cache e a reutiliza para muitos clientes, então a distribuição fica desigual e cega à saúde dos servidores. Use um load balancer atrás do nome.
- **Qualquer coisa secreta.** Os dados do DNS são públicos por design, e as consultas do DNS clássico trafegam em texto claro. Não coloque ali credenciais nem topologia interna que você não publicaria.

<Callout type="warning">
Um `CNAME` não pode coexistir com outros registros no mesmo nome. É por isso que o ápice de uma zona, que precisa conter os registros `SOA` e `NS`, não pode ser um `CNAME` comum.
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Vantagens**

- Administração descentralizada: cada dono de zona atualiza os próprios dados sem coordenar com mais ninguém.
- O cache agressivo mantém a latência baixa e protege os servidores autoritativos da maior parte da carga.
- A redundância é nativa, já que as zonas são servidas por vários servidores e os resolvers tentam cada um deles.
- Suporte universal — toda plataforma conectada à rede traz um resolver.

**Desvantagens**

- As mudanças têm consistência eventual: por até um TTL, clientes diferentes enxergam respostas diferentes.
- O protocolo original não tem integridade nem confidencialidade; ambas foram adicionadas depois, como extensões separadas que não estão implantadas em todo lugar.
- É uma dependência crítica. Se os servidores autoritativos de uma zona ficarem inacessíveis e os caches expirarem, todos os serviços sob aquele nome desaparecem, mesmo que os serviços em si estejam saudáveis.

</ArticleSection>

<ArticleSection id="trade-offs">

O ajuste central é o **TTL**, o prazo de validade de cada cópia em cache. Um TTL longo significa menos consultas, resoluções mais rápidas e mais resiliência a uma indisponibilidade dos autoritativos, mas mudanças lentas. Um TTL curto torna as mudanças visíveis rapidamente, ao custo de mais consultas, mais latência nos cache misses e uma dependência maior de que os servidores autoritativos estejam acessíveis.

As extensões de segurança trazem seus próprios custos. O **DNSSEC** assina os registros para que os resolvers possam verificar origem e integridade, mas adiciona gestão de chaves e respostas maiores, e deliberadamente não esconde o conteúdo das consultas.

Transportes criptografados como o **DNS over HTTPS (DoH)** protegem o caminho entre o cliente e o resolver, mas não provam que os dados obtidos pelo resolver eram autênticos. <Mark variant="underline" tone="teal">Os dois mecanismos são complementares, não alternativos.</Mark>

</ArticleSection>

<ArticleSection id="real-world-examples">

- **A zona raiz.** A IANA lista 13 autoridades nomeadas de servidores raiz, de `a.root-servers.net` a `m.root-servers.net`, operadas por doze organizações independentes, entre elas Verisign, ICANN, RIPE NCC, NASA e a Universidade de Maryland. Por trás desses 13 nomes há uma rede de centenas de servidores em muitos países.
- **Resolvers recursivos públicos.** O Google Public DNS responde consultas tradicionais via UDP e TCP em `8.8.8.8` e também expõe DoH: um endpoint baseado no padrão em `https://dns.google/dns-query` e uma API JSON em `https://dns.google/resolve`.

</ArticleSection>

<ArticleSection id="implementation-examples">

Uma zona é, literalmente, uma daquelas páginas da agenda, escrita num arquivo de texto. Esta é uma zona mínima no formato padrão de master file; a diretiva `$TTL` define o tempo de vida padrão de cada registro:

```text
$TTL 3600
@     IN  SOA  ns1.example.com. hostmaster.example.com. (
               2026111301 ; serial
               7200       ; refresh
               900        ; retry
               1209600    ; expire
               300 )      ; minimum (TTL das respostas negativas)
@     IN  NS     ns1.example.com.
@     IN  NS     ns2.example.com.
@     IN  A      192.0.2.10
www   IN  CNAME  example.com.
@     IN  MX     10 mail.example.com.
```

Você pode ver a resolução acontecer pela linha de comando com o `dig`:

```bash
# Pergunta ao resolver recursivo configurado e imprime só a resposta
dig +short www.example.com A

# Percorre você mesmo a cadeia de delegação, começando pela raiz
dig +trace www.example.com

# Força a consulta via TCP em vez de UDP
dig +tcp example.com MX
```

A mesma pergunta também pode viajar por HTTPS. Aqui ela vai para a API JSON do Google Public DNS:

```bash
curl 'https://dns.google/resolve?name=example.com&type=A'
```

<Callout type="tip">
Antes de uma migração planejada, reduza o TTL dos registros afetados e espere o TTL antigo expirar. Quando você alterar o registro, os caches vão captar a mudança rapidamente; depois, aumente o TTL de novo.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"As mudanças de DNS se propagam pela internet."** Nada é empurrado. Cada cache apenas mantém a sua cópia até o TTL expirar e então pergunta de novo. O "tempo de propagação" é só o TTL restante do registro antigo.
- **"Existem apenas 13 servidores raiz."** Existem 13 *nomes* de servidores raiz; cada um é servido por muitas máquinas ao redor do mundo.
- **"O DNS só usa UDP."** UDP é o caso comum, mas TCP é um transporte obrigatório, usado para respostas grandes e sempre que uma resposta é truncada.
- **"O DNSSEC criptografa o DNS."** O DNSSEC fornece autenticação da origem dos dados e integridade. Ele explicitamente não fornece confidencialidade — consultas e respostas continuam legíveis.
- **"O resolver recursivo é dono dos dados."** Resolvers apenas fazem cache. A fonte da verdade são sempre os servidores autoritativos da zona.

<Callout type="info">
Dados autoritativos sempre prevalecem sobre dados em cache quando um resolver tem os dois — o cache é uma otimização, nunca uma segunda fonte da verdade.
</Callout>

</ArticleSection>
