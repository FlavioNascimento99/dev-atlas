<ArticleSection id="overview">

Think about how you call a friend. You don't type their phone number. You tap their name in your contacts, and the phone finds the number for you.

The internet works the same way. You type `www.example.com`, but your computer can only connect to a number: an **IP address**. Something has to turn the name into that number.

That something is the **Domain Name System (DNS)**, the <Mark variant="highlight" tone="brand">contact list of the internet</Mark>. It maps human-readable names to the data needed to reach a service — most often an IP address, but also mail servers, aliases and free-form text. Programs talk to IP addresses; people and configuration files work with names. DNS is the lookup layer that sits between the two.

There is one big difference from the list on your phone: nobody holds the whole thing. DNS is a <Mark variant="underline" tone="brand">hierarchical, distributed database</Mark>. Its namespace is a tree, and each branch can be handed to a different operator, who then answers only for its own portion.

That design solves two problems at once. First, **indirection**: a name stays stable while the machines behind it change, just as a contact keeps its name when your friend gets a new number. Second, **scale without central control**: no single organization holds all the data.

</ArticleSection>

<ArticleSection id="how-it-works">

Picture that contact list torn into pages, each kept by a different owner. To find a number, someone has to know which owner to ask. DNS has three kinds of participants for that:

- **Resolvers** do the asking. A resolver takes a question from a program and finds the answer on its behalf — the assistant who goes looking up the number for you. The small resolver inside your operating system (a *stub resolver*) usually forwards every question to a **recursive resolver** run by an ISP, a company network or a public provider.
- **Name servers** keep the pages. A server is **authoritative** for a **zone** — a contiguous part of the namespace it is responsible for. Every zone is expected to be served by at least two servers for redundancy.
- **Resource records** are the entries on each page. Every record has a name, a type, a **TTL** (time to live) and a value.

The tree is split through <Mark variant="underline" tone="teal">delegation</Mark>: each level says "I don't have that entry, but I know who does". The root zone delegates `com` to the servers of that top-level domain (TLD). Those servers, in turn, delegate `example.com` to the servers of whoever registered it.

Delegations are written as `NS` records, placed at the point where one zone ends and another begins.

When a recursive resolver has nothing cached, it walks this tree from the top. It asks a root server and gets a *referral*, a pointer to the TLD servers. It asks one of them and gets a referral to the domain's authoritative servers. Then, finally, it gets the answer.

How does it know where the top is? It ships with a built-in list of root server names and addresses, called the *root hints*.

Walking the tree on every lookup would be slow, so resolvers remember what they learn. This is **caching**, a lot like saving a number you just looked up. Every record carries a TTL that says how long it may be cached before it must be discarded.

<Mark variant="highlight" tone="brand">Caching is what makes the system fast</Mark>: most questions are answered from the resolver's memory without touching any authoritative server. Even "this name does not exist" answers can be cached, for a time derived from the zone's `SOA` record.

A name can point to more than an address, so records come in types. These are the ones you will meet most often:

Under the hood, queries travel on port 53. Classic DNS over UDP limits a message to 512 bytes. When an answer does not fit, the server sets the truncation (`TC`) flag and the client retries over TCP.

Modern requirements make TCP support mandatory for every general-purpose DNS implementation. It is not an optional fallback.

</ArticleSection>

<ArticleSection id="when-to-use">

If your software talks to another machine, it should almost always find it by name. In practice, DNS is the right tool for:

- **Giving every service a stable name.** Clients should reference `api.example.com`, never a literal IP address. That way <Mark variant="highlight" tone="brand">the infrastructure can move without redeploying clients</Mark>.
- **Coarse traffic steering.** Publishing different or multiple addresses for a name is a simple way to spread clients across regions or providers.
- **Delegating control.** You can hand a subdomain to another team or vendor with `NS` records, or point it at a third-party service with a `CNAME`.
- **Publishing domain-level metadata**, such as mail routing (`MX`) and ownership or policy assertions (`TXT`).

</ArticleSection>

<ArticleSection id="when-not-to-use">

Here the contact-list analogy breaks down. When you edit a contact, your phone sees the change at once. In DNS, copies of the old entry live in caches you don't control. That rules out a few uses:

- **Fast failover.** After a record changes, caches keep serving the old value until its TTL runs out, and you do not control the resolvers that hold it. <Mark variant="highlight" tone="amber">DNS alone cannot move traffic away from a failed host in seconds.</Mark>
- **Per-request load balancing.** A resolver caches one answer and reuses it for many clients, so the distribution is uneven and blind to server health. Use a load balancer behind the name.
- **Anything secret.** DNS data is public by design, and classic DNS queries are sent in clear text. Do not encode credentials or internal topology you would not publish.

<Callout type="warning">
A `CNAME` cannot coexist with other records at the same name. That is why the apex of a zone, which must hold `SOA` and `NS` records, cannot be a plain `CNAME`.
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**Advantages**

- Decentralized administration: each zone owner updates its own data without coordinating with anyone else.
- Aggressive caching keeps latency low and shields authoritative servers from most of the load.
- Redundancy is built in, since zones are served by multiple servers and resolvers retry across them.
- Universally supported — every networked platform ships a resolver.

**Disadvantages**

- Changes are eventually consistent: for up to one TTL, different clients see different answers.
- The original protocol has neither integrity nor confidentiality; both were added later as separate extensions that are not deployed everywhere.
- It is a critical dependency. If the authoritative servers for a zone are unreachable and caches expire, every service under that name disappears, even if the services themselves are healthy.

</ArticleSection>

<ArticleSection id="trade-offs">

The central knob is the **TTL**, the expiry date on every cached copy. A long TTL means fewer queries, faster lookups and more resilience to an authoritative outage, but slow changes. A short TTL makes changes visible quickly, at the cost of more queries, more latency on cache misses and a tighter dependency on the authoritative servers being reachable.

Security extensions bring their own costs. **DNSSEC** signs records so resolvers can verify origin and integrity, but it adds key management and larger responses, and it deliberately does not hide the content of queries.

Encrypted transports such as **DNS over HTTPS (DoH)** protect the path between client and resolver, but they do not prove that the data the resolver obtained was authentic. <Mark variant="underline" tone="teal">The two mechanisms are complementary, not alternatives.</Mark>

</ArticleSection>

<ArticleSection id="real-world-examples">

- **The root zone.** IANA lists 13 named root server authorities, `a.root-servers.net` through `m.root-servers.net`, run by twelve independent operators including Verisign, ICANN, RIPE NCC, NASA and the University of Maryland. Behind those 13 names sits a network of hundreds of servers in many countries.
- **Public recursive resolvers.** Google Public DNS answers traditional UDP and TCP queries at `8.8.8.8` and also exposes DoH: a standards-based endpoint at `https://dns.google/dns-query` and a JSON API at `https://dns.google/resolve`.

</ArticleSection>

<ArticleSection id="implementation-examples">

A zone is literally one of those pages of the contact list, written as a text file. This is a minimal zone in the standard master file format; the `$TTL` directive sets the default lifetime of each record:

```text
$TTL 3600
@     IN  SOA  ns1.example.com. hostmaster.example.com. (
               2026111301 ; serial
               7200       ; refresh
               900        ; retry
               1209600    ; expire
               300 )      ; minimum (TTL of negative answers)
@     IN  NS     ns1.example.com.
@     IN  NS     ns2.example.com.
@     IN  A      192.0.2.10
www   IN  CNAME  example.com.
@     IN  MX     10 mail.example.com.
```

You can watch resolution happen from the command line with `dig`:

```bash
# Ask the configured recursive resolver and print only the answer
dig +short www.example.com A

# Walk the delegation chain yourself, starting at the root
dig +trace www.example.com

# Force the query over TCP instead of UDP
dig +tcp example.com MX
```

The same question can also travel over HTTPS. Here it goes to the Google Public DNS JSON API:

```bash
curl 'https://dns.google/resolve?name=example.com&type=A'
```

<Callout type="tip">
Before a planned migration, lower the TTL of the affected records and wait for the old TTL to elapse. When you change the record, caches will pick it up quickly; raise the TTL again afterwards.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"DNS changes propagate across the internet."** Nothing is pushed. Each cache simply keeps its copy until the TTL expires and then asks again. "Propagation time" is just the remaining TTL of the old record.
- **"There are only 13 root servers."** There are 13 root server *names*; each one is served by many machines around the world.
- **"DNS only uses UDP."** UDP is the common case, but TCP is a required transport, used for large answers and whenever a response is truncated.
- **"DNSSEC encrypts DNS."** DNSSEC provides data origin authentication and integrity. It explicitly does not provide confidentiality — queries and answers remain readable.
- **"The recursive resolver owns the data."** Resolvers only cache. The source of truth is always the zone's authoritative servers.

<Callout type="info">
Authoritative data always wins over cached data when a resolver has both — a cache is an optimization, never a second source of truth.
</Callout>

</ArticleSection>
