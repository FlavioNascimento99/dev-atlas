---
title: "TCP vs UDP"
description: "Reliable, ordered streams versus lightweight, connectionless datagrams."

<ArticleSection id="overview">

**TCP** (Transmission Control Protocol) and **UDP** (User Datagram Protocol) are the two classic transport protocols of the internet. Both sit on top of IP and both use port numbers to deliver data to the right process on a host. They differ in how much they promise.

IP alone is best-effort: packets may be lost, duplicated or arrive out of order. **TCP hides all of that**, giving the application a reliable, in-order stream of bytes over a connection. **UDP hides almost none of it**: it adds ports and a checksum to IP and hands each message to the application as it arrives — or not at all. Choosing between them is choosing who deals with an imperfect network: the operating system's TCP stack, or your application.

</ArticleSection>

<ArticleSection id="how-it-works">

**TCP** is connection-oriented. Before any data flows, the two endpoints run a **three-way handshake** (`SYN`, `SYN-ACK`, `ACK`) that, among other things, exchanges the initial **sequence numbers** each side will use. From then on:

- Every byte is numbered. The receiver sends **cumulative acknowledgments**: acknowledging number X confirms everything before X.
- Data that is not acknowledged in time is **retransmitted**, with a timeout that adapts to the measured round-trip time.
- **Flow control**: each side advertises a receive window, so a fast sender cannot overrun a slow receiver.
- **Congestion control**: the sender probes the capacity of the path, starting with a small window that grows (slow start) and shrinking it when loss signals congestion.
- The connection is closed explicitly, with each side sending a `FIN`.

TCP delivers a **byte stream**, not messages. It does not preserve the boundaries of the application's writes: two `send` calls may arrive as one read, or one `send` as several. Protocols on top of TCP must frame their own messages. The header is at least 20 bytes.

**UDP** is connectionless. Its header is 8 bytes with four fields: source port, destination port, length and checksum. There is no handshake, no acknowledgment, no retransmission, no ordering and no congestion control. The specification is explicit that delivery and duplicate protection are not guaranteed. Each datagram is independent and self-contained, so message boundaries are preserved: one send is one receive.

Everything UDP leaves out becomes optional work for the application. A protocol that needs only some of TCP's guarantees can build exactly those and skip the rest.

</ArticleSection>

</ArticleSection>

<ArticleSection id="when-to-use">

**Choose TCP when** every byte must arrive and order matters: web pages and APIs, file transfer, e-mail, database connections, remote shells. It is the right default — the reliability machinery is already written, tuned and running in the kernel.

**Choose UDP when:**

- **Late data is useless data.** In live audio, video and game state updates, a retransmitted packet arrives too late to matter; it is better to skip it and move on.
- **The exchange is a single small request and response**, such as a DNS query, where a connection handshake would cost more than the exchange itself.
- **You are building your own transport** with different trade-offs than TCP — which is what QUIC does.

</ArticleSection>

<ArticleSection id="when-not-to-use">

- **Do not pick UDP "for speed" when you need reliability.** You will end up re-implementing acknowledgments, retransmission, ordering and congestion control — badly, compared to decades of TCP engineering.
- **Do not send bulk data over raw UDP without congestion control.** UDP has none built in, and the IETF usage guidelines place the responsibility on the application to control its rate and avoid harming other traffic.
- **Do not use TCP for strictly real-time media** where a stall is worse than a glitch: a single lost packet delays everything behind it.
- **Do not open a new TCP connection for every tiny exchange** if you can reuse one; each new connection pays a full round trip before any data.

<Callout type="warning">
UDP flows have no connection teardown, so NAT devices and stateful firewalls drop their mappings on a timer. Long-lived UDP sessions need keepalives, and peer-to-peer UDP needs NAT traversal techniques.
</Callout>

</ArticleSection>

<ArticleSection id="advantages-and-disadvantages">

**TCP — advantages**

- Reliable, ordered delivery with no application code.
- Built-in flow and congestion control make it a good network citizen by default.
- Works practically everywhere; middleboxes understand it.

**TCP — disadvantages**

- A round trip of latency before the first byte of data.
- Head-of-line blocking: one lost packet stalls the whole stream.
- No message boundaries; applications must frame their data.

**UDP — advantages**

- No setup cost and minimal header overhead.
- Message boundaries preserved; no head-of-line blocking between datagrams.
- Full control: the application decides what, if anything, to retransmit.

**UDP — disadvantages**

- No delivery, ordering or duplicate guarantees.
- No congestion control unless the application adds it.
- Datagrams should stay below the path MTU, which limits message size.

</ArticleSection>

The real trade-off is **latency predictability versus completeness**. TCP converts packet loss into delay; UDP converts it into missing data. Neither removes the loss. A second axis is **where the complexity lives**: TCP puts it in the kernel, shared and hard to change; UDP lets it live in the application, where it can evolve quickly but must be built and maintained.

</ArticleSection>

<ArticleSection id="real-world-examples">

- **DNS** is the best-known everyday user of UDP: browsers depend on it to turn hostnames into addresses before any connection is made.
- **WebRTC** brings real-time voice, video and peer-to-peer data to the browser over UDP, because those applications tolerate some loss in exchange for low latency.
- **QUIC** is a full transport built on UDP datagrams. It provides ordered byte streams, loss recovery and congestion control, but makes streams independent of one another.
- **HTTP/3** maps HTTP onto QUIC. With HTTP/2 over a single TCP connection, a lost packet stalls every active request; with HTTP/3, a stream that suffers loss does not prevent progress on the others.

</ArticleSection>

<ArticleSection id="implementation-examples">

The difference is visible in the sockets API. A TCP client connects first and then reads a stream, so it must loop until it has a complete message:

```python
import socket

with socket.create_connection(("example.com", 80)) as sock:  # three-way handshake
    sock.sendall(b"HEAD / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")
    response = b""
    while chunk := sock.recv(4096):  # a stream: read until the peer closes
        response += chunk

print(response.decode())
```

A UDP client has no connection. Each `sendto` is one datagram, each `recvfrom` returns exactly one datagram, and the application must handle silence itself:

```python
import socket

with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as sock:
    sock.settimeout(2)  # no reply may ever arrive
    sock.sendto(b"ping", ("192.0.2.10", 9999))
    try:
        data, addr = sock.recvfrom(1500)  # one whole datagram
        print(data, addr)
    except TimeoutError:
        print("lost request or lost reply - retry or give up")
```

<Callout type="tip">
If you need "UDP, but reliable", look for an existing protocol first — QUIC for general transport, WebRTC for real-time media — before designing your own.
</Callout>

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"UDP is faster than TCP."** Packets travel at the same speed. UDP avoids the handshake and never waits for retransmissions; whether that is "faster" depends on whether your application can live with missing data.
- **"TCP sends messages."** TCP sends a byte stream. One write does not correspond to one read; framing is the application's job.
- **"UDP means unreliable applications."** UDP is an unreliable *transport*. QUIC shows that fully reliable protocols can be built on top of it.
- **"TCP guarantees delivery."** TCP guarantees that data is delivered in order *or* that the connection reports failure. It cannot deliver across a broken path.

<Callout type="important">
Reliability is not free and not binary. TCP bundles ordering, retransmission, flow control and congestion control into one package; UDP lets you choose which of them you actually need.
</Callout>

</ArticleSection>
