title: "Microservices Architecture"
description: "Structuring an application as independently deployable services."

<ArticleSection id="overview">

A **microservices architecture** builds one application as a suite of small services. Each service runs in its own process, is organized around a business capability, owns its data and can be deployed without redeploying the others. Services talk to each other through lightweight mechanisms, most often HTTP APIs or messaging.

The style is defined in contrast with the **monolith**, an application built and deployed as a single unit. In a monolith, a change to one small part means rebuilding and redeploying everything, and scaling means replicating the whole application even if only one part is under load. As the codebase and the number of people working on it grow, module boundaries tend to erode and teams step on each other's releases. Microservices attack that problem by turning module boundaries into process boundaries.

<Callout type="important">
The defining property is **independent deployability**, not size. A service that cannot be released without coordinating with three others is not delivering the benefit of the style, however small it is.
</Callout>

</ArticleSection>

<ArticleSection id="how-it-works">

James Lewis and Martin Fowler's 2014 article describes the style through a set of common characteristics rather than a formal definition. The ones that shape the mechanics most are:

- **Componentization via services.** The unit of composition is a separately running service with a published interface, instead of a library linked into one process.
- **Organized around business capabilities.** A service covers a slice of the business (orders, payments, catalog) end to end, and one cross-functional team owns it. This follows Conway's law: system design mirrors the organization's communication structure, so teams split by technical layer produce layered systems with cross-team hand-offs.
- **Smart endpoints and dumb pipes.** Domain logic lives in the services. The transport — HTTP or a lightweight message broker — only carries messages, in contrast with an Enterprise Service Bus that holds routing and business rules in the middleware.
- **Decentralized data management.** Each service manages its own data store and no other service reads it directly. Cross-service transactions are avoided in favour of eventual consistency and compensating operations.
- **Infrastructure automation.** Many services released often are only manageable with automated build, test and deployment pipelines.
- **Design for failure.** Any remote call can fail, so callers use timeouts, circuit breakers and bulkheads and are expected to degrade gracefully.

Keeping data private is the hardest rule to live with. Queries that used to be a `JOIN` now need an API that composes results from several services, or a read model built from events those services publish. A business operation that spans services becomes a **saga**: a sequence of local transactions with compensations if a step fails.

</ArticleSection>

<ArticleSection id="when-to-use">

- **Many teams working on the same product.** Service boundaries let each team build, test and release on its own schedule. Fowler notes that strong module boundaries matter most as teams get larger.
- **Parts of the system with clearly different needs.** One capability must scale far beyond the rest, needs a different data store or changes much more often.
- **A domain you already understand.** Service boundaries are expensive to move, so they should be drawn where the business boundaries have proven stable.
- **Mature delivery and operations.** Automated provisioning, deployment pipelines and monitoring are already in place.

</ArticleSection>

<ArticleSection id="when-not-to-use">

- **A new product with an unproven domain.** Fowler's "monolith first" argument is that boundaries are hard to get right up front and that refactoring across services is much harder than inside a monolith.
- **A small team.** The overhead of running a distributed system slows a team that could simply share one codebase.
- **No automation.** Without continuous delivery and monitoring, dozens of services multiply manual work and blind spots.
- **Workflows that need strong consistency across the whole dataset.** Splitting the data forces you to rebuild with sagas what a single database transaction gave you for free.

<Callout type="tip">
A well-modularized monolith is a legitimate destination, not just a stepping stone. It keeps in-process calls and single-database transactions, and services can still be peeled off later where the pressure is real.
</Callout>

</ArticleSection>

<ArticleSection id="trade-offs">

**Granularity.** Smaller services are easier to understand and replace, but every boundary adds a network hop, a deployment pipeline and an interface to version. Too fine a split recreates coupling as chatty call chains.

**Autonomy versus consistency.** Private databases let teams change schemas freely; the price is that joins and transactions move into application code as API composition and sagas.

**Local simplicity versus global complexity.** Each service is simpler than the monolith it replaced, but the complexity does not disappear: it moves into the interactions between services, where it is harder to see and to test.

**Technology freedom versus fragmentation.** Every extra language or database is one more thing the organization must know how to run, secure and hire for.

<Callout type="warning">
The failure mode to avoid is the **distributed monolith**: services that share a database or must be deployed together. It pays every cost of distribution while giving up independent deployment.
</Callout>

</ArticleSection>

<ArticleSection id="real-world-examples">

- Lewis and Fowler name **Amazon, Netflix, The Guardian** and the **UK Government Digital Service** among the organizations pioneering the style. They cite Amazon's "two pizza team" rule for team size, and Netflix's Simian Army, which injects failures into production to test that services tolerate them.
- **Uber** moved from two monolithic services to microservices around 2012–2013 to address availability risks, costly deployments and slow team execution. By 2020 it reported about 2,200 critical microservices, and described a new problem: understanding a single issue could require working through around 50 services owned by 12 teams. Its answer, Domain-Oriented Microservice Architecture, groups services into domains exposed through a single gateway each.

Uber's account is a useful reminder that the style solves organizational scaling problems and, at sufficient scale, creates new ones.

</ArticleSection>

<ArticleSection id="implementation-examples">

"Design for failure" in practice: a call to another service with a timeout and a fallback, in TypeScript. The page still renders if the recommendations service is slow or down.

```ts
export async function getRecommendations(userId: string): Promise<string[]> {
  try {
    const response = await fetch(`http://recommendations.internal/users/${userId}`, {
      signal: AbortSignal.timeout(300), // never wait more than 300 ms
    })
    if (!response.ok) return []
    return (await response.json()) as string[]
  } catch {
    return [] // timeout or network failure: degrade instead of failing
  }
}
```

A saga with a compensation, where a failed stock reservation refunds the payment already charged:

```ts
type Payments = {
  charge(orderId: string): Promise<void>
  refund(orderId: string): Promise<void>
}
type Inventory = { reserve(orderId: string): Promise<void> }

export async function placeOrder(orderId: string, payments: Payments, inventory: Inventory): Promise<'confirmed' | 'rejected'> {
  await payments.charge(orderId)
  try {
    await inventory.reserve(orderId)
    return 'confirmed'
  } catch {
    await payments.refund(orderId) // compensate the step that already succeeded
    return 'rejected'
  }
}
```

A production saga also has to persist its progress, so that a crash between the charge and the refund can be resumed.

</ArticleSection>

<ArticleSection id="common-misconceptions">

- **"Micro means few lines of code."** The original article gives no size rule. The useful measure is whether one team can own the service and release it alone.
- **"Microservices are required to scale."** A monolith can be replicated behind a load balancer. What microservices add is scaling parts independently — and scaling the number of teams.
- **"Each service needs its own database server."** The requirement is that data is private to the service. Private tables or a schema per service on a shared server satisfy it, as long as access is actually restricted.
- **"Microservices make the system simpler."** They make each piece simpler and the whole more complex.
- **"Successful companies started this way."** Fowler observes that most success stories began as a monolith that grew too large and was then broken up.
- **"Containers and Kubernetes are microservices."** Those are deployment tools. They can run a monolith just as well, and using them does not create service boundaries.

</ArticleSection>
